    8. Hilos de ejecución

    Este capítulo presenta la ejecución simultánea de varios fragmentos de código dentro de un mismo programa: los hilos (threads, o hilos de ejecución) y las herramientas para sincronizarlos. Hace unos veinte años, la mayoría de las máquinas tenían un solo procesador, y el paralelismo era en gran medida una ilusión mantenida por el sistema operativo. Hoy, incluso la computadora portátil más básica tiene varios núcleos: varios hilos se ejecutan realmente al mismo tiempo, lo que hace aún más frecuentes los problemas de sincronización que se tratan aquí.

    Java admite hilos desde su primera versión (1996): la clase [Thread], la palabra clave [synchronized] y los métodos [wait] / [notify] de la clase [Object]. Java 5 (2004) agregó el paquete [java.util.concurrent] y sus subpaquetes [java.util.concurrent.locks] y [java.util.concurrent.atomic]: bloqueos (locks), semáforos, colecciones concurrentes, grupos de hilos (thread pools), etc. Java 7 agregó el framework [Fork/Join], Java 8 introdujo los streams paralelos y Java 21 introdujo los hilos virtuales, todo lo cual ha cambiado profundamente la forma de escribir servidores. Por último, Java 25 introduce los valores acotados a un ámbito ([ScopedValue]). Exploraremos todas estas herramientas en este capítulo.

    Los ejemplos son archivos fuente compactos ([java Threads01.java]) ubicados en la carpeta [08-threads]. Recuerde que un archivo fuente compacto importa automáticamente todo el módulo [java.base]: por lo tanto, las clases de los paquetes [java.util.concurrent], [java.util.concurrent.locks], [java.util.concurrent.atomic] y [java.time] pueden usarse sin la directiva [import].

    Una advertencia antes de empezar: los resultados de un programa multihilo varían de una ejecución a otra. El orden en que se asigna el procesador a los hilos depende del sistema operativo, del número de procesadores y de la carga de la máquina. Los resultados mostrados en este capítulo se obtuvieron en una máquina Linux de dos procesadores compartida con otros programas muy activos. Si usted ejecuta los ejemplos, obtendrá resultados similares, pero rara vez idénticos. Indicaremos en cada caso qué es reproducible y qué no.

    8.1. La clase Thread

    Cuando se inicia una aplicación, esta se ejecuta en un flujo de ejecución llamado hilo (thread). La clase de Java que modela un hilo es la clase [java.lang.Thread]. Sus principales constructores y métodos son los siguientes:

    Los métodos [join] y [sleep] lanzan la excepción verificada [InterruptedException] si el hilo es interrumpido durante la espera: el compilador exige que se maneje o se declare. Hablaremos de su significado en la sección sobre interrupciones.

    La clase [Thread] también tiene un método, [stop], que antes terminaba un hilo por la fuerza. Está obsoleto desde Java 1.2 y, desde Java 20, simplemente lanza la excepción [UnsupportedOperationException]: detener un hilo de forma abrupta podría dejar los datos que estaba manejando en un estado inconsistente. Hoy, se le pide a un hilo que se detenga de forma cooperativa mediante interrupción: lo veremos un poco más adelante.

    8.2. Creación de hilos de ejecución

    Es posible tener aplicaciones en las que fragmentos de código se ejecutan «simultáneamente» en distintos hilos de ejecución. Si la máquina tiene menos procesadores que hilos listos para ejecutarse, los hilos se reparten los procesadores: cada uno accede a un procesador por turnos durante un breve instante (unos pocos milisegundos). En una máquina multiprocesador, varios hilos se ejecutan realmente al mismo tiempo. El tiempo asignado a un hilo depende de varios factores, entre ellos su prioridad, que tiene un valor predeterminado pero puede establecerse mediante programación ([setPriority]); esto es solo una indicación, que el sistema operativo es libre de ignorar (Linux la ignora de forma predeterminada). Un hilo que tiene acceso al procesador puede liberarlo antes de tiempo:

    • esperando un evento (la finalización de otro hilo mediante [join], la espera de una señal);
    • durmiendo durante un período determinado ([sleep]).

    Un hilo T se crea primero, por ejemplo, mediante el constructor [new Thread(task, name)], donde [task] es un objeto que implementa la interfaz funcional [Runnable], cuyo único método es [void run()]. Este objeto suele ser una lambda o una referencia a un método (las interfaces funcionales se introdujeron en el capítulo 7). En código más antiguo, también pueden encontrarse clases derivadas de *[Thread]* que redefinen su método *[run]*: esto no se recomienda, porque mezcla la tarea que se debe realizar con el medio para ejecutarla.

    Crear un hilo no lo inicia:

    • la ejecución del hilo T se inicia mediante [T.start()]: el método [run] de la tarea pasada al constructor de T será entonces ejecutado por el hilo T. El código que ejecuta la instrucción [T.start()] no espera a que el hilo T termine: pasa de inmediato a la siguiente instrucción. Ahora tenemos dos hilos ejecutándose en paralelo. A menudo necesitan comunicarse entre sí para seguir el avance del trabajo compartido: este es el problema de la sincronización de hilos;
    • una vez iniciado, el hilo T se ejecuta de forma autónoma. Se detiene cuando el método que está ejecutando termina;
    • podemos esperar a que termine de ejecutarse mediante [T.join()]. Esta es una instrucción bloqueante: el hilo que la ejecuta se bloquea hasta que el hilo T haya terminado su trabajo. Este es un método básico de sincronización.

void main() {
    // se nombra el hilo principal
    Thread.currentThread().setName("Main");

    // creación de 5 hilos
    var tasks = new Thread[5];
    for (int i = 0; i < tasks.length; i++) {
        // el hilo n.º i ejecutará el método display; se le asigna el nombre "i"
        tasks[i] = new Thread(this::display, String.valueOf(i));
        // se inicia su ejecución (operación no bloqueante)
        tasks[i].start();
    }

    // fin del hilo principal
    IO.println("End of thread " + Thread.currentThread().getName() + " at " + time());
}

// el método ejecutado por los hilos: tiene la firma de Runnable.run()
void display() {
    // el hilo que ejecuta el método
    Thread current = Thread.currentThread();
    IO.println("Start of execution of the display method in thread " + current.getName()
            + " (id " + current.threadId() + ") : " + time());
    // espera de 1 s
    sleep(1000);
    IO.println("End of execution of the display method in thread " + current.getName()
            + " : " + time());
}

// espera de [ms] milisegundos
static void sleep(long ms) {
    try {
        Thread.sleep(ms);
    } catch (InterruptedException e) {
        // la espera fue interrumpida: se restablece el indicador de interrupción del hilo
        Thread.currentThread().interrupt();
    }
}

// la hora actual, al milisegundo
static String time() {
    return LocalTime.now().format(DateTimeFormatter.ofPattern("HH:mm:ss.SSS"));
}

Escribimos [this::display] porque, en un archivo fuente compacto, los métodos declarados fuera de cualquier clase son métodos de instancia de la clase implícita, cuyo nombre no puede utilizarse en el código. El segundo parámetro del constructor es el nombre del hilo;
    • línea 13: se lanza el hilo n.º i. Esta operación no es bloqueante: el hilo n.º i se ejecuta en paralelo con el hilo principal que lo lanzó;
    • línea 17: el hilo principal llega al final del programa;
    • Líneas 21–30: el método [display] muestra el nombre y el ID del hilo que lo ejecuta, así como las horas de inicio y fin (al milisegundo) de la ejecución;
    • línea 27: todo hilo que ejecuta el método [display] se detiene durante 1 segundo. El procesador se cede entonces a otro hilo que espera el procesador. Al final de la pausa de 1 segundo, el hilo en pausa vuelve a ser elegible para obtener el procesador. Lo obtendrá cuando le llegue el turno;

El método [run] de [Runnable] no declara ninguna excepción verificada: por lo tanto, el método [display] no puede dejar escapar la excepción [InterruptedException] lanzada por [sleep] . Encontraremos este pequeño método en la mayoría de los programas de este capítulo;

    • En primer lugar, vemos que lanzar un hilo no es bloqueante. El hilo principal lanzó 5 hilos y llegó al final del programa (línea 6) aunque el hilo 3 aún no había mostrado su primer mensaje;
    • el orden de ejecución de los hilos es impredecible: en esta ejecución, el hilo 4 mostró su mensaje de inicio antes que el hilo 0. Aquí el sistema operativo tiene 6 hilos y 2 procesadores; asigna los procesadores a estos hilos según sus propias reglas;
    • También observamos que el orden de las salidas no siempre sigue el orden de las horas mostradas: el hilo principal mostró su finalización a las 13.725, después de mensajes fechados de 13.727 a 13.732. La hora se calcula antes de la salida y, mientras tanto, otro hilo puede haber escrito en la consola. [IO.println] (como [System.out.println]) es seguro para hilos (thread-safe): dos líneas escritas por dos hilos no se mezclan, pero su orden no está garantizado;
    • los ID de los hilos creados (22 a 26) muestran que la máquina virtual ya había creado unos veinte hilos para sus propios fines (recolección de basura, compilador just-in-time, etc.);
    • cada hilo se detiene durante un segundo en [sleep] y luego termina la ejecución del método [display];
    • Por último, el programa no se detuvo cuando el hilo principal terminó su trabajo: la máquina virtual esperó a que los cinco hilos terminaran. Esto se debe a que estos hilos no son hilos daemon: la máquina virtual de Java se detiene cuando todos sus hilos no daemon han terminado.

void main() {

}

    8.3. Detener un hilo: la interrupción

    ¿Cómo se detiene un hilo antes de que termine su trabajo, por ejemplo, cuando el usuario cancela una operación larga? Java no permite matar un hilo; en su lugar, ofrece un mecanismo cooperativo llamado interrupción:

    • Cada hilo tiene un indicador de interrupción, un booleano inicialmente establecido en [false];
    • un hilo T1 que quiere detener al hilo T2 llama a [T2.interrupt()]. Esto activa el indicador de interrupción de T2. Se trata de una solicitud de terminación: T2 no es terminado; corresponde a ese hilo decidir cuándo y cómo terminar, de modo que deje sus datos en un estado consistente;
    • si T2 está bloqueado en un método de espera ([sleep], [join], [wait] y la mayoría de los métodos bloqueantes de [java.util.concurrent]), se lo despierta: el método lanza la excepción [InterruptedException] y el indicador de interrupción se restablece a [false];
    • si T2 realiza un cálculo sin esperar nunca, debe verificar su propio indicador mediante [Thread.currentThread().isInterrupted()] a intervalos regulares.

    Por eso los métodos bloqueantes declaran la excepción verificada [InterruptedException]: el compilador exige que el programador decida qué hacer con una solicitud de detención. Hay dos respuestas correctas: dejar que la excepción se propague al llamador (declarándola en la cláusula [throws]), o interceptarla y completar la tarea de forma limpia. Cuando ninguna de las dos opciones es posible, como en el método [sleep] del programa anterior, el indicador se restablece mediante [Thread.currentThread().interrupt()] para que el código llamador aún pueda ver la solicitud. La única respuesta incorrecta es ignorar la excepción. El programa [Threads05.java] demuestra los tres casos:

    8.4. Hilos virtuales

    Los hilos que hemos creado hasta ahora son hilos de plataforma: cada uno es un envoltorio de un hilo del sistema operativo, que ocupa durante toda su vida útil. Un hilo del sistema es un recurso costoso: crearlo lleva tiempo, su pila reserva memoria (del orden de un megabyte) y el sistema no puede administrar eficientemente más que unos pocos miles de ellos. Sin embargo, un servidor que dedica un hilo a cada cliente (véase el diagrama del párrafo siguiente) pasa la mayor parte del tiempo esperando: la respuesta de una base de datos, la siguiente solicitud del cliente… Durante estas esperas, el hilo del sistema permanece bloqueado e inutilizable.

    Java 21 introdujo los hilos virtuales («virtual threads», JEP 444). Un hilo virtual es un objeto [Thread] como cualquier otro, pero lo administra la máquina virtual de Java en lugar del sistema operativo:

    • para ejecutarse, un hilo virtual se monta sobre un hilo de plataforma, llamado su «hilo portador» (carrier thread). Los hilos portadores forman un grupo pequeño, cuyo tamaño predeterminado es el número de procesadores;
    • cuando un hilo virtual se bloquea ([sleep], espera de E/S de red, un bloqueo, una cola bloqueante, etc.), se desmonta: su pila se aparta en la memoria de la máquina virtual y el hilo portador queda disponible de inmediato para otro hilo virtual. Cuando termina la espera, el hilo virtual se vuelve a asociar a un hilo anfitrión, no necesariamente el mismo;
    • un hilo virtual ocupa unos cientos de bytes: se pueden crear millones.

    8.5. Beneficios de los hilos

    Ahora que hemos puesto de relieve la existencia de un hilo predeterminado (el que ejecuta el método [main]) y que sabemos cómo crear otros, consideremos los beneficios de los hilos. Tienen dos usos principales:

    • aprovechar todos los procesadores de la máquina para un cálculo que consume mucho tiempo: el trabajo se divide en partes asignadas a distintos hilos. Lo haremos mediante streams paralelos y el framework [Fork/Join] al final de este capítulo;
    • realizar varias tareas simultáneamente, en particular cuando algunas de ellas consisten principalmente en esperar (una respuesta de red, una lectura de disco o una entrada del usuario). Este es el caso de las aplicaciones cliente/servidor de Internet, que trataremos en el capítulo 12.

    Utilizamos todos los días aplicaciones de Internet que siguen este esquema: servicios web, correo electrónico, transferencias de archivos, etc. En el diagrama anterior, el servidor S1 debe atender simultáneamente a los clientes Ci. No es solo una cuestión de sincronización temporal: como veremos en la sección sobre la palabra clave [volatile], una escritura realizada por un hilo no es necesariamente visible para otro. El modelo de memoria de Java garantiza que todo lo que escribe un hilo es visible para el hilo que esperó su finalización mediante [join], y que todo lo que escribe el hilo lanzador antes de [start] es visible para el hilo lanzado. Más adelante exploraremos otras formas de sincronizar.

    En lugar de una lambda, podríamos escribir una clase que implemente [Runnable] y cuyos campos contengan la información intercambiada. La lambda es más concisa; es el enfoque más común hoy en día. Para recuperar el resultado de un procesamiento, también veremos más adelante la interfaz [Callable<V>], cuyo método [V call()] devuelve un resultado.

    8.7. Acceso concurrente a recursos compartidos

    8.7.1. Acceso concurrente sin sincronización

    En la sección anterior, la información se intercambiaba solo entre dos hilos y en momentos muy específicos: era un ejemplo clásico de paso de parámetros.     • un hilo T1 comienza a actualizar la estructura S: modifica el campo I1 y es interrumpido antes de completar la actualización de toda la estructura S;

    8.7.3. La clase ReentrantLock

    El bloqueo [synchronized] es simple pero rígido: un hilo que espera un monitor espera indefinidamente, sin poder desistir tras cierto tiempo y sin poder ser interrumpido.     8.7.4. Sincronización de procesos: el bloqueo de archivo

    Los bloqueos descritos hasta ahora sincronizan hilos dentro de una misma máquina virtual, es decir, dentro de un mismo proceso. A veces diferentes procesos necesitan compartir un recurso, como un archivo, o se desea impedir que se inicien dos instancias de una misma aplicación. Java no ofrece un objeto de sincronización con nombre compartido entre procesos; en su lugar se utiliza un bloqueo de archivo administrado por el sistema operativo: la clase [java.nio.channels.FileLock]. Se obtiene un bloqueo sobre un archivo abierto en forma de canal [FileChannel]:

    • [FileLock lock()]: espera a que el bloqueo esté disponible y lo adquiere;
    • [FileLock tryLock()]: intenta adquirir el bloqueo sin esperar y devuelve [null] si otro proceso lo posee;
    • [void release()]: libera el bloqueo. El bloqueo también se libera cuando se cierra el canal o cuando el proceso termina, incluso de forma abrupta: un bloqueo no puede quedar “abandonado”.

        // intento sin espera: null si otro proceso tiene el bloqueo

            IO.println(time() + " : process " + process + " obtained the lock, it works for 3 s");
            Thread.sleep(3000);
            IO.println(time() + " : process " + process + " releases the lock");
        } finally {
            lock.release();
        }
    }
}

    8.7.5. Una barrera: la clase Semaphore

    Un semáforo es un contador de permisos (o plazas). La clase [java.util.concurrent.Semaphore] ofrece los siguientes métodos:

    Miembro
    Función
    [Semaphore(int permits)], [Semaphore(int permits, boolean fair)]
    crea un semáforo con [permits] permisos; el segundo parámetro tiene el mismo significado que en [ReentrantLock]
    [void acquire()]
    adquiere un permiso. Si no quedan permisos, el hilo queda bloqueado hasta que se libere uno. La espera puede ser interrumpida ([InterruptedException])
    [void acquireUninterruptibly()]
    igual que el anterior, pero la espera no puede ser interrumpida
    [boolean tryAcquire()], [boolean tryAcquire(long timeout, TimeUnit unit)]
    obtiene un permiso de inmediato, o como máximo dentro de [timeout]; devuelve [false] si el intento falla
    [void release()]
    devuelve (agrega) un permiso; uno de los hilos en espera puede entonces tomarlo
    [int availablePermits()]
    el número de permisos disponibles

    A diferencia de un bloqueo, un permiso no pertenece a ningún hilo en particular: cualquier hilo puede llamar a [release], incluso si nunca ha adquirido un permiso. Un semáforo creado con cero permisos es, por lo tanto, una barrera cerrada, en la que los hilos que llaman a [acquire] quedan bloqueados. Otro hilo la abrirá cuando llegue el momento, llamando a [release]. Este momento depende por completo del problema que se resuelva. El hilo que adquirió el único permiso atravesó la barrera, que se cerró tras él; al devolver el permiso, abre la barrera para otro hilo.     8.7.6. Las clases CountDownLatch y Semaphore

    Dos usos adicionales de las herramientas de sincronización complementan los ejemplos anteriores.

    Un objeto [java.util.concurrent.CountDownLatch] es un contador: se crea con un valor inicial N; cada llamada a su método [countDown] lo decrementa; su método [await] bloquea al hilo que lo llama hasta que el contador llega a 0.     8.7.7. Visibilidad de las escrituras: la palabra clave volatile

    Los bloqueos no sirven solo para hacer indivisible un grupo de operaciones. Resuelven un segundo problema, más insidioso: la visibilidad de las escrituras. Para acelerar la ejecución, el procesador almacena valores en sus registros y cachés, y el compilador reordena o elimina lecturas y escrituras sobre la marcha, como vimos con el programa [Threads09.java]. Como resultado, un valor escrito por un hilo puede no ser visto por otro hilo hasta más tarde, o quizá nunca.

    El Modelo de memoria de Java define con precisión cuándo se garantiza que una escritura sea visible: cuando existe una relación “happens-before” entre la escritura y la lectura. Las principales son las siguientes:

    • todo lo que un hilo ha hecho antes de liberar un bloqueo (fin de un bloque [synchronized], [unlock]) es visible para el hilo que adquiere posteriormente ese bloqueo;
    • lo que el hilo llamador hizo antes de [start] es visible para el hilo llamado; lo que un hilo hizo es visible para el hilo que esperó su finalización mediante [join];
    • una escritura en un campo [volatile] es visible para cualquier lectura posterior de ese campo;
    • las herramientas de [java.util.concurrent] ofrecen garantías similares: lo que un hilo hizo antes de [release()], [countDown()], o de la inserción de un elemento en una colección concurrente, es visible para el hilo que ejecuta posteriormente [acquire()], [await()], o que retira el elemento.

    Cuando no existe ninguna de estas relaciones, se dice que el programa contiene una “carrera de datos” (data race) y no hay ninguna garantía. El programa [Threads16.java] lo ilustra con un escenario común: un indicador que ordena a un hilo detenerse.

    8.7.8. Clases atómicas

    El paquete [java.util.concurrent.atomic] (Java 5) proporciona clases que hacen atómicas las operaciones simples sobre una variable: la operación se ejecuta por completo en el hilo, sin que ningún otro hilo pueda observar o modificar la variable en medio de la operación. Las herramientas anteriores ([synchronized], [ReentrantLock], [Semaphore]) están diseñadas para hacer atómico un grupo de operaciones, al costo de bloquear a otros hilos. Para operaciones simples pero frecuentes, las clases atómicas evitan este bloqueo mediante instrucciones especiales del procesador. Los principales métodos de la clase [AtomicInteger] son los siguientes:

    Método
    Función
    [int get()], [void set(int v)]

    [int incrementAndGet()], [int decrementAndGet()]

    8.8. Acceso concurrente a varios recursos compartidos

    8.8.1. Interbloqueo

    En nuestros ejemplos anteriores, se compartía un único recurso entre los distintos hilos. La situación se complica si hay varios recursos y dependen unos de otros. En particular, puede producirse un interbloqueo (deadlock): dos hilos se esperan mutuamente. Considere las siguientes acciones, que ocurren de forma secuencial:

    • un hilo T1 adquiere el bloqueo V1 para acceder a un recurso compartido R1;
    • un hilo T2 adquiere el bloqueo V2 para acceder a un recurso compartido R2;
    • el hilo T1 solicita el bloqueo V2. Queda bloqueado;
    • el hilo T2 solicita el bloqueo V1. Queda bloqueado.

    Los hilos T1 y T2 se esperan mutuamente de forma indefinida. Hay varias soluciones posibles:

    • solicitar ambos recursos a la vez mediante un único bloqueo. Esto no siempre es posible si implica un bloqueo prolongado de un recurso costoso;
    • adquirir siempre los bloqueos en el mismo orden: si todos los hilos adquieren V1 antes que V2, el interbloqueo es imposible. Esta es la regla más utilizada;
    • un hilo que posee V1 y no puede adquirir V2 libera V1 para evitar el interbloqueo.

// toma el 1.er recurso y luego intenta tomar el 2.º durante [timeout]
static void work(Lock first, String firstName, Lock second, String secondName, Duration timeout) {
    String name = Thread.currentThread().getName();
    first.lock();
    try {
        IO.println(time() + " : " + name + " obtained " + firstName);
        // se da tiempo al otro hilo para que tome su primer recurso
        Thread.sleep(500);
        IO.println(time() + " : " + name + " requests " + secondName);
        // solicitud con un tiempo máximo de espera, en lugar de un lock() que esperaría indefinidamente
        if (second.tryLock(timeout.toMillis(), TimeUnit.MILLISECONDS)) {
            try {
                IO.println(time() + " : " + name + " obtained " + secondName
                        + " and works with " + firstName + " and " + secondName);
            } finally {
                second.unlock();
            }
        } else {
            IO.println(time() + " : " + name + " did not obtain " + secondName + " within " + timeout.toSeconds()
                    + " s: it releases " + firstName + " and gives up");
        }
    } catch (InterruptedException e) {
        Thread.currentThread().interrupt();
    } finally {
        first.unlock();
    }
}

    8.8.2. Un ejemplo: lectores y escritores

    Considere el siguiente ejemplo:

    • tenemos un arreglo en el que algunos hilos escriben datos (los escritores) y otros los leen (los lectores);
    • los escritores son iguales entre sí pero exclusivos: solo un escritor a la vez puede escribir datos en el arreglo;
    • los lectores son iguales entre sí pero exclusivos: solo un lector a la vez puede leer los datos almacenados en el arreglo;
    • un lector solo puede leer datos del arreglo cuando un escritor ha colocado algunos allí, y un escritor solo puede colocar nuevos datos en el arreglo cuando los datos que ya están allí han sido leídos por un lector.

    Hay dos tipos de recursos compartidos:

    • la tabla de escritura: solo un escritor a la vez puede acceder a ella;
    • la tabla de lectura: solo un lector a la vez puede acceder a ella.

    y un orden de utilización de estos recursos:

    • un lector debe seguir siempre a un escritor;
    • un escritor debe seguir siempre a un lector, excepto la primera vez.

    El acceso a estos dos recursos puede controlarse mediante dos barreras de tipo [Semaphore]:

    • cuando un escritor ha terminado su trabajo, abre la barrera [canRead] para dejar entrar a un lector;
    • cuando un lector ha terminado su trabajo, abre la barrera [canWrite] para dejar entrar a un escritor.

    8.8.3. Los métodos wait y notifyAll

    En el ejemplo anterior, cuando los escritores están bloqueados en la instrucción [canWrite.acquireUninterruptibly()], uno de ellos, cualquiera, es desbloqueado por la operación [canWrite.release()]. Si se desea abrir la barrera para un escritor específico, las cosas se complican.

    Consideremos la analogía de una oficina de servicios públicos con ventanillas de atención. Cuando llega un cliente, toma un número del dispensador y luego va a sentarse. A los clientes se les llama por su número mediante un altavoz. Mientras espera, el cliente puede hacer lo que quiera: puede leer o dormitar. Se despierta cada vez que el altavoz anuncia un número. Si es su número, el cliente se levanta y va a la ventanilla; de lo contrario, vuelve a lo que estaba haciendo. Podemos proceder de manera similar con los hilos. Tomemos el ejemplo de los escritores:

    En la ventanilla
    Con hilos
    varios escritores esperan en la misma ventanilla
    sus hilos están bloqueados
    la ventanilla queda disponible y se llama al número del siguiente escritor
    el hilo que estaba leyendo el arreglo notifica a los escritores que el arreglo está disponible. Ese hilo u otro ha determinado qué escritor debe continuar
    Cada escritor verifica su número; solo el que tiene el número llamado pasa a la ventanilla; los demás vuelven a la cola de espera
    Cada hilo verifica si es el elegido. Si lo es, atraviesa la barrera; de lo contrario, vuelve a la cola de espera

    Describiremos ahora un patrón estándar, presentado en particular en el libro de Brian Goetz et al., [Java Concurrency in Practice], que permite resolver problemas de barreras con condiciones de entrada.

    Los hilos que comparten un recurso (el mostrador) acceden a él mediante un objeto que llamaremos token: es un objeto simple ([new Object()]) cuyo monitor se utiliza. Para cruzar la barrera que lleva al mostrador, hay que tener el token, y solo hay uno. Por lo tanto, los hilos deben pasarse el token entre sí.

    Para ir al mostrador, un hilo solicita primero el token mediante un bloque [synchronized (token)]. Si obtiene el token, verifica en un bucle [while (!iAmTheExpectedOne) { token.wait(); }] si cumple la condición para pasar al mostrador y luego pasa al mostrador, siempre dentro del bloque [synchronized]. Si el hilo no es el esperado en el mostrador, cede su turno devolviendo el token mediante [token.wait()] y entra en el estado bloqueado. Será despertado cuando otro hilo señale un cambio en la condición de acceso; recuperará entonces el token y verificará de nuevo la condición. Por eso la prueba es un bucle ([while]) y no un simple [if]. Hay una segunda razón, propia de Java: la especificación admite los “despertares espurios” (spurious wakeups), en los que [wait] termina sin que ningún hilo haya llamado a [notify]; el bucle los vuelve inofensivos. La operación [token.wait()] solo puede ser realizada por un hilo que posea el monitor del token; de lo contrario, se lanza una excepción [IllegalMonitorStateException]. En este esquema, el token solo se libera una vez finalizada la transacción.

    El hilo que modifica la condición de acceso al mostrador también debe poseer el token y notificar a los hilos en espera: dentro de un bloque [synchronized (token)], modifica la condición de acceso al mostrador y luego despierta a los hilos en espera mediante [token.notifyAll()].

    Despertar a los hilos significa que los hilos en espera pasan a ser candidatos al token; no lo reciben de inmediato. El token solo queda disponible al final del bloque [synchronized]. Todos los hilos despertados recibirán entonces el token por turnos, en un orden indeterminado, lo que les da la oportunidad de verificar de nuevo la condición de acceso. El primero que cumpla la condición conserva el token y pasa a la fila.

static class Board {
    // el arreglo compartido entre lectores y escritores
    private static final int[] data = new int[3];
    // los testigos de acceso de los contadores de lectura y escritura
    private static final Object canRead = new Object();
    private static final Object canWrite = new Object();
    // las condiciones de acceso de los contadores
    private static boolean readingAllowed = false;
    private static boolean writingAllowed = false;
    private static int nextReader = 0;
    private static int nextWriter = 0;
    // el orden de los lectores y de los escritores
    static List<String> readOrder = List.of();
    static List<String> writeOrder = List.of();

    // abre el contador de escritura
    static void allowWriting() {
        synchronized (canWrite) {
            writingAllowed = true;
            // se despierta a todos los escritores que esperan el testigo
            canWrite.notifyAll();
        }
    }

    // leer el contenido del arreglo
    static void read() {
        String name = Thread.currentThread().getName();
        IO.println("Method [read] started by thread " + name);
        // se solicita el testigo del contador de lectura
        synchronized (canRead) {
            try {
                // mientras no sea nuestro turno, se devuelve el testigo y se espera
                while (!readingAllowed || !readOrder.get(nextReader).equals(name)) {
                    canRead.wait();
                }
            } catch (InterruptedException e) {
                return;
            }
            // en el contador: lectura del arreglo
            for (int i = 0; i < data.length; i++) {
                sleep(500);
                IO.println(time() + " : reader " + name + " read the number " + data[i]);
            }
            // siguiente lector
            readingAllowed = false;
            nextReader++;
            // se notifica a los escritores que pueden escribir
            synchronized (canWrite) {
                writingAllowed = true;
                canWrite.notifyAll();
            }
            IO.println("Method [read] finished by thread " + name);
        }
    }

    // escribir en el arreglo
    static void write() {
        String name = Thread.currentThread().getName();
        IO.println("Method [write] started by thread " + name);
        // se solicita el testigo del contador de escritura
        synchronized (canWrite) {
            try {
                // mientras no sea nuestro turno, se devuelve el testigo y se espera
                while (!writingAllowed || !writeOrder.get(nextWriter).equals(name)) {
                    canWrite.wait();
                }
            } catch (InterruptedException e) {
                return;
            }
            // en el contador: escritura del arreglo
            for (int i = 0; i < data.length; i++) {
                sleep(500);
                data[i] = ThreadLocalRandom.current().nextInt(0, 1000);
                IO.println(time() + " : writer " + name + " wrote the number " + data[i]);
            }
            // siguiente escritor
            writingAllowed = false;
            nextWriter++;
            // se notifica a los lectores que pueden leer
            synchronized (canRead) {
                readingAllowed = true;
                canRead.notifyAll();
            }
            IO.println("Method [write] finished by thread " + name);
        }
    }

    8.8.4. Condiciones: la interfaz Condition

    Los métodos [wait] y [notifyAll] están asociados al monitor de un objeto y, por lo tanto, a los bloques [synchronized]. Para un bloqueo [ReentrantLock], el equivalente es la interfaz [java.util.concurrent.locks.Condition]: un objeto [Condition] se crea con el método [newCondition()] del bloqueo y proporciona los métodos [await()] (el equivalente de [wait]), [await(long time, TimeUnit unit)], [signal()] (el equivalente de [notify]) y [signalAll()] (el equivalente de [notifyAll]). Su uso sigue las mismas reglas: el hilo debe poseer el bloqueo, y la condición de acceso se prueba dentro de un bucle [while].

    La ventaja principal es que un único bloqueo puede tener varias condiciones, es decir, varias colas distintas. En nuestro problema, un único bloqueo puede proteger ambos mostradores, con una condición para los lectores y otra para los escritores: un lector que termina despierta a los escritores, y solo a los escritores. static class Board {
    // el arreglo compartido entre lectores y escritores
    private static final int[] data = new int[3];
    // un único bloqueo para ambos contadores
    private static final ReentrantLock lock = new ReentrantLock();
    // dos condiciones asociadas a este bloqueo: dos colas de espera distintas
    private static final Condition canRead = lock.newCondition();
    private static final Condition canWrite = lock.newCondition();
    // las condiciones de acceso de los contadores
    private static boolean readingAllowed = false;
    private static boolean writingAllowed = false;
    private static int nextReader = 0;
    private static int nextWriter = 0;
    // el orden de los lectores y de los escritores
    static List<String> readOrder = List.of();
    static List<String> writeOrder = List.of();

    // abre el contador de escritura
    static void allowWriting() {
        lock.lock();
        try {
            writingAllowed = true;
            // se despierta a todos los escritores, y solo a ellos
            canWrite.signalAll();
        } finally {
            lock.unlock();
        }
    }

    // leer el contenido del arreglo
    static void read() {
        String name = Thread.currentThread().getName();
        IO.println("Method [read] started by thread " + name);
        lock.lock();
        try {
            // mientras no sea nuestro turno, se devuelve el bloqueo y se espera una señal
            while (!readingAllowed || !readOrder.get(nextReader).equals(name)) {
                canRead.await();
            }
            // en el contador: lectura del arreglo
            for (int i = 0; i < data.length; i++) {
                sleep(500);
                IO.println(time() + " : reader " + name + " read the number " + data[i]);
            }
            // siguiente lector
            readingAllowed = false;
            nextReader++;
            // se notifica a los escritores que pueden escribir
            writingAllowed = true;
            canWrite.signalAll();
            IO.println("Method [read] finished by thread " + name);
        } catch (InterruptedException e) {
            Thread.currentThread().interrupt();
        } finally {
            lock.unlock();
        }
    }

    // escribir en el arreglo
    static void write() {
        String name = Thread.currentThread().getName();
        IO.println("Method [write] started by thread " + name);
        lock.lock();
        try {
            // mientras no sea nuestro turno, se devuelve el bloqueo y se espera una señal
            while (!writingAllowed || !writeOrder.get(nextWriter).equals(name)) {
                canWrite.await();
            }
            // en el contador: escritura del arreglo
            for (int i = 0; i < data.length; i++) {
                sleep(500);
                data[i] = ThreadLocalRandom.current().nextInt(0, 1000);
                IO.println(time() + " : writer " + name + " wrote the number " + data[i]);
            }
            // siguiente escritor
            writingAllowed = false;
            nextWriter++;
            // se notifica a los lectores que pueden leer
            readingAllowed = true;
            canRead.signalAll();
            IO.println("Method [write] finished by thread " + name);
        } catch (InterruptedException e) {
            Thread.currentThread().interrupt();
        } finally {
            lock.unlock();
        }
    }

    8.8.5. Varios lectores simultáneos: ReadWriteLock

    En los ejemplos anteriores, los lectores eran exclusivos. En muchas aplicaciones, esto es innecesariamente restrictivo: varios hilos pueden leer datos al mismo tiempo mientras nadie los modifica. Solo las escrituras deben ser exclusivas: mientras un escritor modifica los datos, ningún lector ni otro escritor debe poder acceder a ellos. Este es el problema clásico de lectura-escritura, que resuelve la interfaz [java.util.concurrent.locks.ReadWriteLock]. Un objeto [ReadWriteLock] proporciona dos bloqueos vinculados:

    • [readLock()]: el bloqueo de lectura, que puede ser poseído por varios hilos al mismo tiempo, siempre que ningún hilo posea el bloqueo de escritura;
    • [writeLock()]: el bloqueo de escritura, que es exclusivo.

    private final Map<String, Integer> prices = new HashMap<>(Map.of("keyboard", 20, "mouse", 10));
    // un bloqueo para los lectores, un bloqueo para los escritores
    private final ReadWriteLock lock = new ReentrantReadWriteLock();

    // varios hilos pueden tener el bloqueo de lectura al mismo tiempo
    int read(String article) {
        String name = Thread.currentThread().getName();
        lock.readLock().lock();

            IO.println(time() + " : " + name + " starts reading the price of " + article);

            lock.readLock().unlock();
        }

        lock.writeLock().lock();

            IO.println(time() + " : " + name + " set the price of " + article + " to " + newPrice);
        } finally {
            lock.writeLock().unlock();
        }

    8.9. Colecciones concurrentes

    Los ejemplos anteriores protegían datos compartidos muy simples (un contador, un arreglo, un pequeño diccionario). Cuando los hilos comparten una colección (lista, diccionario, cola), se podría proteger cada acceso con un bloqueo. Sin embargo, las colecciones estándar ([ArrayList], [HashMap], [ArrayDeque]) no están diseñadas para ser modificadas por varios hilos simultáneamente: su uso sin protección puede provocar la pérdida de elementos, desencadenar excepciones inesperadas ([ConcurrentModificationException]) o incluso corromper la estructura interna de la colección. Los métodos [Collections.synchronizedList(…)], [Collections.synchronizedMap(…)]… envuelven una colección normal en un objeto donde cada método es [synchronized]: esto es seguro, pero todos los hilos compiten por un único bloqueo, y la iteración sobre la colección debe seguir protegiéndose manualmente. Desde Java 5, el paquete [java.util.concurrent] ofrece colecciones diseñadas para ser compartidas entre hilos sin un bloqueo explícito:

    8.9.2. Productor y consumidores: BlockingQueue

    El problema de los lectores y los escritores es una variante del clásico problema productor-consumidor: unos hilos producen datos que otros hilos consumen. La interfaz [BlockingQueue<E>] lo resuelve sin ninguna herramienta de sincronización explícita:

    • [put(element)] agrega un elemento a la cola. Si la cola tiene una capacidad limitada y está llena, el productor queda bloqueado hasta que haya un espacio disponible;
    • [take()] retira el elemento que está al frente de la cola. Si la cola está vacía, el consumidor queda bloqueado hasta que llegue un elemento;
    • [offer(element, timeout, unit)] y [poll(timeout, unit)] hacen lo mismo, con un tiempo máximo de espera; [offer(element)] y [poll()], que no tienen tiempo de espera, nunca bloquean: devuelven [false] o [null] en caso de fallo.

    La cola no sabe que la producción ha terminado. Una técnica clásica consiste en colocar en la cola, al final de la producción, un valor especial, conocido en el mundo anglosajón como “poison pill”: el consumidor que lo recupera sabe que debe detenerse. Otra técnica consiste en interrumpir a los consumidores, ya que [take] es interrumpible. El programa [Threads24.java] es el siguiente:

// el valor que señala el fin de la producción ("poison pill")
static final int END = -1;

void main() throws InterruptedException {
    // una cola de 3 elementos como máximo
    BlockingQueue<Integer> queue = new ArrayBlockingQueue<>(3);
    final int nbConsumers = 2;

    // el productor coloca 8 números y luego señala que ha terminado
    var producer = new Thread(() -> {
        try {
            for (int i = 1; i <= 8; i++) {
                // bloqueante si la cola está llena
                queue.put(i);
                IO.println(time() + " : P put " + i
                        + " (waiting elements: " + queue.size() + ")");
                Thread.sleep(100);
            }
            // un marcador de fin por consumidor
            for (int i = 0; i < nbConsumers; i++) {
                queue.put(END);
            }
            IO.println(time() + " : P has finished");
        } catch (InterruptedException e) {
            Thread.currentThread().interrupt();
        }
    }, "P");

    // dos consumidores toman los números hasta el marcador de fin
    var consumers = new Thread[nbConsumers];
    for (int i = 0; i < consumers.length; i++) {
        consumers[i] = new Thread(() -> {
            String name = Thread.currentThread().getName();
            try {
                while (true) {
                    // bloqueante si la cola está vacía
                    int number = queue.take();
                    if (number == END) {
                        break;
                    }
                    IO.println(time() + " : " + name + " took " + number);
                    // procesamiento del número
                    Thread.sleep(600);
                }
                IO.println(time() + " : " + name + " has finished");
            } catch (InterruptedException e) {
                Thread.currentThread().interrupt();
            }
        }, "C" + (i + 1));
    }

    // inicio de todos los hilos y espera de su fin
    producer.start();
    for (Thread consumer : consumers) {
        consumer.start();
    }
    producer.join();
    for (Thread consumer : consumers) {
        consumer.join();
    }
}

    8.10. Pools de hilos: ExecutorService

    8.10.1. El principio

    Hasta ahora, para administrar hilos, los hemos creado y luego iniciado mediante [start()]. Crear un hilo de plataforma es una operación relativamente costosa: en particular, el sistema debe asignarle una pila, y cada hilo ocupa memoria mientras exista. Veremos en el capítulo 10 que existen pools de conexiones: las conexiones abiertas se mantienen en reserva y se prestan a los hilos que las solicitan, ya que abrir una conexión es costoso. Existe un sistema similar para los hilos: el pool de hilos.

    Java representa un pool de hilos mediante la interfaz [java.util.concurrent.ExecutorService] (un “ejecutor”): ya no se crean hilos; en su lugar, se asignan tareas al ejecutor, que hace que sus hilos las ejecuten. Un hilo que ha completado una tarea no se destruye; pasa a la siguiente tarea. La clase [ThreadPoolExecutor], la implementación más común, funciona de la siguiente manera:

    • tiene un número fijo de hilos (“core pool size”): mientras no se haya alcanzado este número, cada nueva tarea provoca la creación de un nuevo hilo;
    • una vez superado, las tareas se colocan en una cola (una [BlockingQueue]) de la que los hilos las recuperan;
    • si la cola está llena, el pool crea hilos adicionales, hasta un número máximo (“maximum pool size”). Estos hilos adicionales se destruyen si permanecen inactivos durante más de cierto tiempo;
    • si se alcanza el máximo y la cola está llena, la tarea es rechazada: de forma predeterminada, el método que la envió lanza la excepción [RejectedExecutionException].

    El pool de hilos ofrece dos ventajas: ahorra el tiempo dedicado a crear hilos (unos pocos hilos pueden atender cientos de solicitudes) y, al limitar el número de hilos, evita que la aplicación se vea desbordada por demasiadas solicitudes.

    Un ejecutor termina mediante su método [shutdown] (deja de aceptar nuevas tareas y sus hilos se detienen una vez completadas las tareas ya enviadas), seguido opcionalmente de [awaitTermination] (que espera a que las tareas terminen), o mediante [shutdownNow] (que interrumpe las tareas en curso). A partir de Java 19, [ExecutorService] extiende la interfaz [AutoCloseable]: su método [close] llama a [shutdown] y luego espera a que todas las tareas terminen. Por lo tanto, se puede declarar un ejecutor en una instrucción [try] con recurso: al salir del bloque, todas las tareas asignadas están completadas. El programa [Threads25.java] es el siguiente:

void main() throws InterruptedException {
    IO.println("Main thread: " + Thread.currentThread());

    // 1 - un grupo de 2 hilos, cerrado automáticamente al final del bloque try
    try (ExecutorService pool = Executors.newFixedThreadPool(2)) {

        var futures = new ArrayList<Future<Integer>>();
        for (int i = 0; i < 3; i++) {
            int number = i;
            futures.add(pool.submit(() -> {
                IO.println(time() + " : task " + number + " runs in thread "
                        + Thread.currentThread().getName());
                // trabajo: un Callable puede lanzar excepciones verificadas
                Thread.sleep(500L * (number + 1));
                // el resultado de la tarea
                return number * 10;
            }));
        }
        // los resultados: get() espera el fin de la tarea
        for (int i = 0; i < futures.size(); i++) {
            Future<Integer> future = futures.get(i);
            try {
                IO.println("task " + i + " : result " + future.get() + ", state " + future.state());
            } catch (ExecutionException e) {
                IO.println("task " + i + " failed: " + e.getCause());
            }
        }

        // una tarea que lanza una excepción
        Future<Integer> failing = pool.submit(() -> fail());
        try {
            failing.get();
        } catch (ExecutionException e) {
            // la excepción de la tarea se envuelve en una ExecutionException
            IO.println(e.getClass().getSimpleName() + " containing " + e.getCause().getClass().getSimpleName()
                    + " : " + e.getCause().getMessage());
        }
        IO.println("failing task: state " + failing.state());
    }

    // 2 - un hilo virtual por tarea; invokeAll envía una colección de tareas y espera su fin
    try (ExecutorService executor = Executors.newVirtualThreadPerTaskExecutor()) {
        List<Callable<String>> jobs = new ArrayList<>();
        for (int i = 0; i < 3; i++) {
            int number = i;
            jobs.add(() -> {
                Thread.sleep(300);
                return "job " + number + " executed by " + Thread.currentThread();
            });
        }
        for (Future<String> future : executor.invokeAll(jobs)) {
            // la tarea ha terminado: resultNow() devuelve su resultado sin esperar
            IO.println(future.resultNow());
        }
    }
}

    8.11.2. Divide y vencerás: ForkJoinPool y RecursiveTask

    Los streams paralelos se basan en el framework Fork/Join (Java 7), que también puede utilizarse directamente. Es muy adecuado para algoritmos de «divide y vencerás»: una tarea demasiado grande se descompone en subtareas, que a su vez se descomponen, hasta que los fragmentos son lo bastante pequeños para procesarse directamente; luego se combinan los resultados de las subtareas. Una tarea es una clase derivada de [RecursiveTask<V>] (una tarea que devuelve un resultado de tipo V) o de [RecursiveAction] (sin resultado), en la que se redefine el método [compute]. En [compute], el método [fork()] de una subtarea la envía de inmediato al pool, y su método [join()] espera su resultado.

    Las tareas son ejecutadas por un [ForkJoinPool], en el que cada hilo tiene su propia cola de tareas. Un hilo que se queda sin trabajo «roba» tareas de la cola de otro hilo («work stealing»): de este modo la carga se distribuye automáticamente. Los hilos portadores de los hilos virtuales también forman un [ForkJoinPool]: es el que vimos en la representación textual de los hilos virtuales ([ForkJoinPool-1-worker-1]). // una tarea que cuenta los números primos del intervalo [start, end[
static class CountPrimes extends RecursiveTask<Integer> {
    @Serial
    private static final long serialVersionUID = 1L;
    // por debajo de este umbral, el fragmento se procesa directamente
    private static final int THRESHOLD = 100_000;
    // el número de fragmentos procesados por cada hilo
    static final Map<String, Integer> chunks = new ConcurrentHashMap<>();

    private final int start;
    private final int end;

    CountPrimes(int start, int end) {
        this.start = start;
        this.end = end;
    }

    @Override
    protected Integer compute() {
        // fragmento suficientemente pequeño: se procesa de forma secuencial
        if (end - start <= THRESHOLD) {
            chunks.merge(Thread.currentThread().getName(), 1, Integer::sum);
            int nb = 0;
            for (int i = start; i < end; i++) {
                if (isPrime(i)) {
                    nb++;
                }
            }
            return nb;
        }
        // de lo contrario, se divide en dos
        int middle = (start + end) >>> 1;
        var left = new CountPrimes(start, middle);
        var right = new CountPrimes(middle, end);
        // la mitad izquierda se entrega al grupo (otro hilo puede "robarla")
        left.fork();
        // la mitad derecha la procesa el hilo actual
        int nbRight = right.compute();
        // se espera el resultado de la mitad izquierda y se combinan los dos resultados
        return left.join() + nbRight;
    }
}

// prueba de primalidad (deliberadamente simple)
static boolean isPrime(int n) {
    if (n < 2) {
        return false;
    }
    for (int d = 2; d * d <= n; d++) {
        if (n % d == 0) {
            return false;
        }
    }
    return true;
}

// el número de milisegundos transcurridos desde [start] (en nanosegundos)
static long since(long start) {
    return (System.nanoTime() - start) / 1_000_000;
}

    8.12. Datos locales al hilo

    8.12.1. El principio

    Consideremos una aplicación de tres capas:

    Supongamos que la aplicación es multiusuario, como una aplicación web. Cada solicitud de usuario es atendida por un hilo. El ciclo de vida del hilo es el siguiente:

    • el hilo se crea (hilo virtual) o se solicita a un pool de hilos para atender la solicitud de un usuario;
    • si esta solicitud requiere datos, el hilo ejecuta un método de la capa [ui], que llama a un método de la capa [business], que a su vez llama a un método de la capa [dao];
    • el hilo devuelve la respuesta al usuario. Luego, o bien termina, o bien se devuelve al pool de hilos.

    Durante el segundo paso, puede ser útil que el hilo tenga sus propios datos, es decir, datos no compartidos con otros hilos. Estos datos podrían, por ejemplo, pertenecer al usuario específico al que atiende el hilo y utilizarse en las distintas capas [ui, business, dao] sin pasarlos como parámetro a cada método.

    Java ofrece dos herramientas para este fin:

    • La clase [ThreadLocal<T>] (Java 1.2): un objeto cuyo valor —leído con [get()] y escrito con [set(value)]— es diferente para cada hilo. El constructor [ThreadLocal.withInitial(supplier)] proporciona el valor inicial para cada hilo; el método [remove()] borra el valor del hilo actual. La clase derivada [InheritableThreadLocal<T>] transmite el valor que tiene el hilo creador al hilo recién creado;
    • la clase [ScopedValue<T>] (definitiva en Java 25): un valor enlazado, durante un ámbito delimitado del código, a un hilo, y que no puede modificarse dentro de ese ámbito.

    8.12.3. La clase ScopedValue

    Un valor [ScopedValue<T>] se enlaza a un valor durante la ejecución de un fragmento de código, llamado su ámbito:

    • [ScopedValue.newInstance()] crea un valor enlazable, normalmente almacenado en un campo [static final];
    • [ScopedValue.where(sv, value).run(action)] ejecuta la acción (un [Runnable]) enlazando [sv] a [value]. Durante la ejecución de la acción —y de todos los métodos que esta llama— en el hilo actual, [sv.get()] devuelve [value]. Cuando la acción termina, el enlace desaparece: no hay nada que limpiar;
    • [ScopedValue.where(sv, value).call(op)] hace lo mismo con una operación que devuelve un resultado;
    • Dentro del ámbito, el valor no puede modificarse; solo puede enlazarse a otro valor para un ámbito anidado;
    • [isBound()] indica si el valor está enlazado en el hilo actual; [orElse(other)] devuelve el valor o, si no está enlazado, [other]. Fuera de cualquier ámbito, [get()] lanza la excepción [NoSuchElementException].

Podemos adoptar otro enfoque:

    • incluir en la capa [dao] únicamente las operaciones básicas (insertar, actualizar, eliminar y leer un artículo);
    • trasladar a la capa [business] las operaciones que actualizan varios artículos simultáneamente. Estas operaciones utilizan las operaciones básicas de la capa [dao].

    La ventaja de esta solución es que la misma capa [dao] puede utilizarse sin modificaciones con diferentes capas [business]. Introduce, sin embargo, una dificultad en la gestión de la transacción que agrupa las actualizaciones que deben realizarse de forma atómica:

    • la transacción debe ser iniciada por la capa [business] antes de que esta llame a los métodos de la capa [dao];
    • los métodos de la capa [dao] deben conocer la existencia de la transacción para poder participar en ella;
    • la transacción debe ser finalizada (confirmada o cancelada) por la capa [business].

    Para que los métodos de la capa [dao] conozcan cualquier transacción en curso, se podría agregar la transacción como parámetro a cada método de la capa [dao]. Este parámetro aparecería entonces en la firma de los métodos de la interfaz, vinculando así la interfaz a una fuente de datos específica. Los datos locales al hilo ofrecen una solución más elegante: la capa [business] coloca la transacción en los datos locales al hilo, y de ahí la recupera la capa [dao]. Las firmas de los métodos de la capa [dao] no necesitan modificarse. Varios hilos (varios usuarios) pueden trabajar simultáneamente: cada uno tiene su propia transacción.

// una transacción simulada: registra cómo deshacer cada actualización
static class Transaction {
    private static final AtomicInteger counter = new AtomicInteger();
    private final Deque<Runnable> undos = new ArrayDeque<>();
    private final int number = counter.incrementAndGet();

    int getNumber() {
        return number;
    }

    // registra la operación que deshace una actualización
    void log(Runnable undo) {
        undos.push(undo);
    }

    // confirma la transacción: las actualizaciones se conservan
    void commit() {
        undos.clear();
    }

    // revierte la transacción: las actualizaciones se deshacen, de la última a la primera
    void rollback() {
        Runnable undo;
        while ((undo = undos.poll()) != null) {
            undo.run();
        }
    }
}

static class Dao implements IDao {
    // la tabla, compartida por todos los hilos, y su bloqueo
    private final List<Article> table = new ArrayList<>();
    private final Object lock = new Object();
    private int nextId = 1;

    @Override
    public int insertArticle(Article article) {
        // ¿hay una transacción en curso en el hilo actual?
        Transaction transaction = ThreadContext.transaction.get();
        synchronized (lock) {
            if (table.stream().anyMatch(a -> a.name().equals(article.name()))) {
                throw new IllegalStateException("an article named [" + article.name() + "] already exists");
            }
            Article inserted = new Article(nextId++, article.name(), article.price(),
                    article.currentStock(), article.minimumStock());
            table.add(inserted);
            // en una transacción, se registra cómo deshacer la inserción
            if (transaction != null) {
                transaction.log(() -> {
                    synchronized (lock) {
                        table.remove(inserted);
                    }
                });
            }
            String mode = transaction == null
                    ? "outside a transaction"
                    : "in transaction " + transaction.getNumber();
            IO.println("[" + Thread.currentThread().getName() + "] [dao] insertion of " + inserted.name()
                    + " (id " + inserted.id() + ") " + mode);
            return 1;
        }
    }

    @Override
    public List<Article> getAllArticles() {
        synchronized (lock) {
            return List.copyOf(table);
        }
    }

    @Override
    public void deleteAllArticles() {
        synchronized (lock) {
            table.clear();
        }
    }
}

interface IBusiness {
    void insertArticlesInTransaction(List<Article> articles);

    void insertArticlesOutOfTransaction(List<Article> articles);

    List<Article> getAllArticles();

    void deleteAllArticles();
}

static class Business implements IBusiness {
    private final IDao dao;

    Business(IDao dao) {
        this.dao = dao;
    }

    // inserción de una lista de artículos: todo o nada
    @Override
    public void insertArticlesInTransaction(List<Article> articles) {
        // inicio de la transacción, almacenada en los datos locales al hilo
        var transaction = new Transaction();
        ThreadContext.transaction.set(transaction);
        try {
            for (Article article : articles) {
                // la capa [dao] encontrará la transacción en el hilo
                dao.insertArticle(article);
                // procesamiento simulado, que da tiempo a otros hilos para intervenir
                sleep(200);
            }
            transaction.commit();
            IO.println("[" + Thread.currentThread().getName() + "] [business] transaction "
                    + transaction.getNumber() + " committed");
        } catch (RuntimeException e) {
            transaction.rollback();
            IO.println("[" + Thread.currentThread().getName() + "] [business] transaction "
                    + transaction.getNumber() + " rolled back");
            // la excepción se vuelve a lanzar al llamador
            throw e;
        } finally {
            // el hilo ya no tiene una transacción en curso
            ThreadContext.transaction.remove();
        }
    }

    // inserción de una lista de artículos sin transacción
    @Override
    public void insertArticlesOutOfTransaction(List<Article> articles) {
        for (Article article : articles) {
            dao.insertArticle(article);
        }
    }

    @Override
    public List<Article> getAllArticles() {
        return dao.getAllArticles();
    }

    @Override
    public void deleteAllArticles() {
        dao.deleteAllArticles();
    }
}

    business.deleteAllArticles();

    execute(() -> business.insertArticlesInTransaction(articles));
    displayArticles(business);

    business.deleteAllArticles();
    IO.println("Two simultaneous threads...");
    List<Article> articlesA = List.of(new Article(0, "keyboard", 20, 5, 1), new Article(0, "mouse", 10, 5, 1),
            new Article(0, "keyboard", 20, 5, 1));
    List<Article> articlesB = List.of(new Article(0, "screen", 150, 2, 1));
    var threadA = new Thread(() -> execute(() -> business.insertArticlesInTransaction(articlesA)), "A");
    var threadB = new Thread(() -> execute(() -> business.insertArticlesOutOfTransaction(articlesB)), "B");
    threadA.start();
    Thread.sleep(100);
    threadB.start();
    threadA.join();
    threadB.join();

static void execute(Runnable action) {
    try {
        action.run();
    } catch (RuntimeException e) {
        IO.println("[" + Thread.currentThread().getName() + "] " + e.getClass().getSimpleName()
                + " : " + e.getMessage());
    }
}

    } catch (InterruptedException e) {
        Thread.currentThread().interrupt();

}

    8.12.5. Conclusión

    El ejemplo anterior demostró el valor de los datos locales al hilo para la gestión de transacciones. No debe replicarse exactamente tal como se muestra, pero describe con precisión cómo funcionan los frameworks: la gestión de transacciones de Spring (anotación [@Transactional]) coloca la transacción y la conexión a la base de datos en un [ThreadLocal], que las capas de acceso a datos consultan sin que su código tenga que manipular la transacción; Hibernate puede, de forma similar, asociar la sesión de trabajo con el hilo actual. Volveremos sobre estas herramientas en el capítulo 11. En código nuevo, en particular al usar hilos virtuales, un *[ScopedValue]* es la forma recomendada de transmitir este tipo de información contextual.

    8.13. Lecturas adicionales

    La sincronización de hilos es un campo difícil. Este capítulo ha presentado las principales herramientas; para profundizar:

    • el libro de Brian Goetz y otros, [Java Concurrency in Practice] (Addison-Wesley), que sigue siendo la referencia definitiva sobre el tema, aunque es anterior a los hilos virtuales;
    • la sección «Concurrency» del tutorial de Java de Oracle: Lesson: Concurrency, que está desactualizada pero sigue siendo correcta en lo básico;
    • la documentación del paquete [java.util.concurrent]: Package java.util.concurrent, cuya sección «Memory Consistency Properties» resume las relaciones «happens-before»;
    • las propuestas de mejora de Java (JEP) que introdujeron los hilos virtuales y los valores con ámbito: JEP 444: Virtual Threads y JEP 506: Scoped Values.

    En el código moderno, rara vez se manipulan directamente los objetos [Thread]. En su lugar, se prefieren los executors ([ExecutorService]), los streams paralelos para los cálculos y los hilos virtuales para los procesos de espera. El capítulo siguiente presenta la programación asíncrona mediante la clase [CompletableFuture], que permite encadenar procesos a la finalización de una operación larga (acceso a la red, a una base de datos o a un archivo) sin bloquear un hilo. Sin embargo, los conceptos tratados en este capítulo siguen siendo esenciales: todas estas tareas se ejecutan en hilos, y los datos que comparten deben protegerse con las mismas herramientas ([synchronized], bloqueos, clases atómicas, colecciones concurrentes).
