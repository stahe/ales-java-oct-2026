    7. Interfaces funcionales, lambdas y eventos

    En muchos programas necesitamos pasar a un método no datos sino comportamiento: el criterio de ordenación, la condición de filtrado o el procesamiento que se debe realizar cuando ocurre algo. Java responde a esta necesidad con un concepto sencillo en el que se basa todo este capítulo: la interfaz funcional, es decir, una interfaz que declara un único método abstracto. Un objeto que implementa una interfaz de este tipo “lleva” una función, que puede almacenarse en una variable, pasarse como parámetro, devolverse como resultado de un método y ejecutarse a voluntad.

    Antes de Java 8 (2014), había que escribir una clase —a menudo una clase anónima— por cada comportamiento que se quería expresar, lo cual era verboso. Java 8 introdujo las expresiones lambda y las referencias a métodos, que permiten escribir este comportamiento en una sola línea. Ya las hemos usado sin entrar en detalles con la API Stream en el capítulo 5: en [persons.stream().filter(p -> p.age() >= 18)], pasamos una lambda —es decir, una instancia de una interfaz funcional— al método [filter]. Este capítulo explica lo que hay detrás de esta sintaxis. Concluye con los eventos, que Java maneja mediante “listeners”: objetos —a menudo lambdas— que se registran en un emisor para ser notificados de lo que ocurre en él. Las interfaces gráficas de usuario de Java (Swing, JavaFX) y los frameworks web se basan por igual en este mecanismo: un clic en un botón o la llegada de una solicitud (HTTP) se señalan a los listeners registrados. Este curso no trata las interfaces gráficas de usuario; todos los ejemplos son programas de consola.

    Los programas de este capítulo son archivos fuente compactos ubicados en la carpeta [07-lambdas]. Se ejecutan con [java LambdasNN.java]. Observe que un archivo fuente compacto importa automáticamente todo el módulo [java.base]: las interfaces de los paquetes [java.util.function], [java.util] o [java.util.concurrent] pueden usarse allí sin ninguna instrucción [import].

    7.1. Interfaces funcionales predefinidas

    7.1.1. El concepto de interfaz funcional

    Una interfaz funcional es una interfaz que tiene exactamente un método abstracto. También puede tener tantos métodos [default] y [static] como se desee (véase el capítulo 4): estos no cuentan. Este único método abstracto describe un modelo (también llamado firma o forma) de una función: los tipos de sus parámetros y el tipo de su valor de retorno. Una variable del tipo de la interfaz puede entonces referirse a cualquier objeto que proporcione una función de esta forma y ejecutarla llamando al método.

    El ejemplo más antiguo es la interfaz [java.lang.Runnable], que existe desde Java 1.0 y representa una tarea que se debe ejecutar (volveremos a ella a propósito de los hilos en el capítulo 8). Consta de un único método: [void run();]. Describe una función:

    • sin parámetros;
    • que no devuelve ningún resultado ([void]).

    Hay tres maneras de crear un objeto de tipo [Runnable]:

    • escribir una clase que implemente la interfaz, ya sea con nombre o anónima. Esta era la única forma de hacerlo antes de Java 8;
    • escribir una expresión lambda: [Runnable task = () -> IO.println("task");];
    • escribir una referencia a método a un método existente que tenga la forma correcta: [Runnable task = Functions::display;].

    En los dos últimos casos, el compilador crea por sí mismo el objeto que implementa la interfaz: la lambda o el método referenciado se convierte en el cuerpo del método [run]. La función se ejecuta entonces llamando al método de la interfaz: [task.run()]. A diferencia de otros lenguajes, Java no tiene una sintaxis de llamada específica: el método de la interfaz siempre se llama por su nombre ([run], [apply], [test]…).

    // las interfaces funcionales predefinidas de Java

void main() {
    // 1 - Runnable: sin parámetro, sin resultado: void run()
    Runnable task = new Runnable() {
        @Override
        public void run() {
            Functions.display();
        }
    };
    // forma abreviada: una referencia a método
    task = Functions::display;
    // ejecución: llamamos al único método abstracto de la interfaz
    task.run();

    // 2 - BiFunction<T, U, R>: dos parámetros, un resultado
    BiFunction<Integer, Integer, Integer> operation = Functions::add;
    IO.println("operation.apply(2, 3)=" + operation.apply(2, 3));
    // Supplier<T>: sin parámetro, un resultado
    Supplier<String> greet = Functions::greet;
    IO.println("greet.get()=" + greet.get());
    // versión primitiva: IntBinaryOperator, int applyAsInt(int, int), sin boxing
    IntBinaryOperator multiply = Functions::multiply;
    IO.println("multiply.applyAsInt(2, 3)=" + multiply.applyAsInt(2, 3));

    // 3 - Consumer<T>: un parámetro, sin resultado
    Consumer<String> write = IO::println;
    write.accept("Consumer<String> executed IO.println");

    // 4 - Predicate<T>: un parámetro, un resultado booleano
    Predicate<Integer> isEven = Functions::isEven;
    IO.println("isEven.test(8)=" + isEven.test(8));
    List<Integer> numbers = new ArrayList<>(List.of(3, 8, 1, 6, 5, 4));
    // removeIf de Collection espera un Predicate
    boolean modified = numbers.removeIf(isEven);
    IO.println("even numbers removed: " + modified + ", remaining: " + numbers);

    // 5 - Comparator<T>: dos parámetros T, un resultado int
    List<String> names = new ArrayList<>(List.of("Paul", "Mélanie", "Jo", "Sébastien"));
    names.sort(Functions::compareLengths);
    IO.println("sorted by length: " + names);

    // 6 - una lambda es un objeto: la instancia de una clase generada que implementa la interfaz
    IO.println("class: " + operation.getClass().getName());
    IO.println("interfaces: " + Arrays.toString(operation.getClass().getInterfaces()));
}

class Functions {

    static void display() {
        IO.println("display() executed by Runnable.run()");
    }

    static int add(int n1, int n2) {
        return n1 + n2;
    }

    static int multiply(int n1, int n2) {
        return n1 * n2;
    }

    static String greet() {
        return "Hello";
    }

    static boolean isEven(int n) {
        return n % 2 == 0;
    }

    static int compareLengths(String s1, String s2) {
        return Integer.compare(s1.length(), s2.length());
    }
}

    7.2. Definición de interfaces funcionales propias

    Las interfaces predefinidas suelen ser suficientes, pero usted puede definir las suyas. Basta con escribir una interfaz con un único método abstracto, por ejemplo:

    • [interface Operation { int calculate(int n1, int n2); }]

    Esta interfaz representa una función que recibe dos enteros y devuelve un entero. En comparación con [IntBinaryOperator]*, el tipo *[Operation] tiene un nombre que describe su propósito, su método tiene un nombre descriptivo ([calculate] en lugar de [applyAsInt]*), y sus parámetros tienen nombres ([n1], [n2]) que las herramientas de desarrollo muestran. Va precedida de la anotación [@FunctionalInterface]*: no es obligatoria, pero indica al compilador que verifique que la interfaz sea funcional y documenta la intención del desarrollador.

    Una variable [op] de tipo [Operation] hace referencia a una sola función a la vez. A diferencia de otros lenguajes, que ofrecen “delegados de multidifusión”, Java no ofrece una forma de almacenar varias funciones en una sola variable y ejecutarlas todas con una sola llamada: cuando es necesario, las funciones se colocan en una lista y se ejecutan una por una. Esto es exactamente lo que haremos con los listeners de eventos.

    // definir sus propias interfaces funcionales

void main() {
    // una variable de tipo Operation recibe el método estático increase
    Operation op = Calculations::increase;
    // ejecutamos la operación
    int n = op.calculate(4, 7);
    IO.println("n=" + n);

    // creación de un objeto c1 de tipo Calculations
    var c1 = new Calculations();
    // almacenamos en op el método add del objeto c1
    op = c1::add;
    n = op.calculate(2, 3);
    IO.println("n=" + n);
    // luego el método subtract de c1
    op = c1::subtract;
    n = op.calculate(2, 3);
    IO.println("n=" + n);

    // una variable referencia una sola función: para ejecutar varias, se usa una lista
    List<Operation> operations = new ArrayList<>();
    operations.add(c1::add);
    operations.add(c1::subtract);
    operations.add((n1, n2) -> n1 * n2);
    for (Operation operation : operations) {
        IO.println("-> " + operation.calculate(10, 4));
    }

    // un método default de la interfaz construye una nueva operación
    Operation squaredSum = ((Operation) c1::add).then(x -> x * x);
    IO.println("squaredSum.calculate(1, 2)=" + squaredSum.calculate(1, 2));

    // Operation e IntBinaryOperator tienen la misma forma pero son dos tipos diferentes
    IntBinaryOperator other = op::calculate;
    IO.println("other.applyAsInt(5, 1)=" + other.applyAsInt(5, 1));

    // una interfaz funcional genérica
    Transformation<String, Integer> length = String::length;
    Transformation<Integer, String> stars = "*"::repeat;
    IO.println("length(\"Hello\")=" + length.transform("Hello"));
    IO.println("stars(5)=" + stars.transform(5));
}

// definición de una interfaz funcional: un solo método abstracto
// que acepta dos enteros como parámetros y devuelve un entero
@FunctionalInterface
interface Operation {
    int calculate(int n1, int n2);

    // un método default no cuenta: la interfaz sigue siendo funcional
    default Operation then(IntUnaryOperator next) {
        return (n1, n2) -> next.applyAsInt(calculate(n1, n2));
    }
}

// una interfaz funcional genérica: T -> R
@FunctionalInterface
interface Transformation<T, R> {
    R transform(T value);
}

// una clase cuyos métodos tienen la forma de la interfaz Operation
class Calculations {
    // dos métodos de instancia
    int add(int n1, int n2) {
        IO.println("add(" + n1 + "," + n2 + ")");
        return n1 + n2;
    }

    int subtract(int n1, int n2) {
        IO.println("subtract(" + n1 + "," + n2 + ")");
        return n1 - n2;
    }

    // un método estático
    static int increase(int n1, int n2) {
        IO.println("increase(" + n1 + "," + n2 + ")");
        return n1 + 2 * n2;
    }
}

void main() {
    // 1 - una clase anónima: la clase que implementa la interfaz se escribe en el lugar
    IntBinaryOperator add = new IntBinaryOperator() {
        @Override
        public int applyAsInt(int n1, int n2) {
            return n1 + n2;
        }
    };
    IO.println("anonymous class: add(2, 3)=" + add.applyAsInt(2, 3));

    // 2 - lo mismo con una expresión lambda (Java 8): parámetros -> cuerpo
    IntBinaryOperator subtract = (int n1, int n2) -> {
        return n1 - n2;
    };
    IO.println("block-body lambda: subtract(2, 3)=" + subtract.applyAsInt(2, 3));

    // 3 - los tipos de los parámetros se infieren de la interfaz de destino
    IntBinaryOperator multiply = (n1, n2) -> n1 * n2;
    IO.println("expression-body lambda: multiply(2, 3)=" + multiply.applyAsInt(2, 3));

    // 4 - un solo parámetro: los paréntesis son opcionales
    IntUnaryOperator square = x -> x * x;
    Predicate<String> isEmpty = s -> s.isEmpty();
    IO.println("square(7)=" + square.applyAsInt(7) + ", isEmpty(\"\")=" + isEmpty.test(""));

    // 5 - sin parámetros: paréntesis vacíos
    Supplier<String> greet = () -> "Hello";
    Runnable beep = () -> IO.println("beep!");
    IO.println(greet.get());
    beep.run();

    // 6 - un cuerpo en bloque con varias instrucciones
    BiConsumer<String, Integer> repeat = (text, times) -> {
        for (int i = 0; i < times; i++) {
            IO.print(text);
        }
        IO.println();
    };
    repeat.accept("ab", 3);

    // 7 - parámetros sin nombre (Java 22): no necesitamos sus valores
    BiConsumer<Object, String> listener = (_, _) -> IO.println("event received");
    listener.accept(null, "click");

    // 8 - una lambda pasada directamente como parámetro de un método
    List<Integer> numbers = new ArrayList<>(List.of(3, 8, 1, 6, 5, 4));
    List<Integer> evens = new ArrayList<>(numbers);
    evens.removeIf(n -> n % 2 != 0);
    IO.println("evens: " + evens);
    numbers.sort((n1, n2) -> Integer.compare(n2, n1));
    IO.println("descending order: " + numbers);

    • línea 44: el carácter de guion bajo [_] designa un parámetro anónimo (Java 22). Se usa cuando la firma de la interfaz exige parámetros que la lambda no necesita, lo cual es habitual en los listeners de eventos. Se pueden incluir varios de estos parámetros en la misma lambda;
    • líneas 49–51: el uso más común de las lambdas es pasarlas directamente como parámetros a un método que espera una interfaz funcional.     Repasemos las formas de una expresión lambda:

    Forma
    Ejemplo
    parámetros con tipo, cuerpo de bloque
    [(int a, int b) -> { return a + b; }]
    parámetros sin tipo, cuerpo de expresión
    [(a, b) -> a + b]
    un único parámetro sin tipo
    [x -> x * x]
    sin parámetros
    [() -> "Hello"]
    parámetros anónimos
    [(_, _) -> IO.println("received")]
    Parámetros declarados con [var]
    [(var a, var b) -> a + b]

    Los parámetros son todos con tipo o todos sin tipo: no se pueden mezclar ambos. En un cuerpo de bloque, una lambda que devuelve un resultado debe tener una instrucción [return] en cada ruta de ejecución, igual que un método.

    Una lambda no es exactamente lo mismo que una clase anónima abreviada. En una clase anónima, [this] hace referencia a la instancia de la clase anónima; en una lambda, [this] hace referencia al objeto del método que contiene la lambda. Además, una clase anónima crea un nuevo ámbito: puede declarar una variable con el mismo nombre que una variable del método, lo que una lambda no puede hacer. Por último, una clase anónima puede implementar una interfaz con varios métodos o heredar de una clase abstracta, lo que es imposible con una lambda. En este curso usaremos lambdas siempre que sea posible.

void main() throws Exception {
    // 1 - una lambda no tiene tipo por sí misma: el contexto lo determina
    // var twice = x -> x * 2;  // rechazado: la lambda necesita un tipo de destino
    var twice = (IntUnaryOperator) x -> x * 2;
    IO.println("twice(21)=" + twice.applyAsInt(21));
    // el mismo texto de lambda puede implementar dos interfaces diferentes
    Supplier<String> supplier = () -> "Hello";
    Callable<String> callable = () -> "Hello";
    IO.println(supplier.get() + " / " + callable.call());

    // 2 - parámetros declarados con var (Java 11): permite anotarlos o hacerlos final
    BinaryOperator<String> concatenate = (final var s1, final var s2) -> s1 + s2;
    IO.println(concatenate.apply("lam", "bda"));

    // 3 - los cuatro tipos de referencias a métodos
    // a) método estático: Class::staticMethod
    Function<String, Integer> convert = Integer::parseInt;
    IO.println("convert(\"42\") + 1 = " + (convert.apply("42") + 1));
    // b) método de instancia de un objeto dado: object::method
    String name = "Pierre";
    Supplier<String> inUpperCase = name::toUpperCase;
    IO.println("inUpperCase.get()=" + inUpperCase.get());
    // c) método de instancia de un objeto arbitrario: Class::instanceMethod
    //    el objeto sobre el que se llama el método pasa a ser el primer parámetro
    UnaryOperator<String> upperCase = String::toUpperCase;
    Comparator<String> ignoreCase = String::compareToIgnoreCase;
    IO.println("upperCase(\"paul\")=" + upperCase.apply("paul")

    // d) constructor: Class::new
    Supplier<List<String>> createList = ArrayList::new;
    Function<String, StringBuilder> createBuffer = StringBuilder::new;
    IntFunction<int[]> createArray = int[]::new;
    List<String> list = createList.get();
    list.add("element");
    IO.println(list + " " + createBuffer.apply("abc").reverse() + " " + createArray.apply(3).length);

    Callable<Integer> read = () -> {

    Supplier<String> r1 = name::toUpperCase;
    Supplier<String> r2 = name::toUpperCase;

Por eso [main] se declara como [throws Exception] (línea 3): las llamadas a [callable.call()] (línea 11) y [read.call()] (línea 44) podrían teóricamente lanzar cualquier [Exception], que el [catch] de la línea 45 —limitado a [IOException]— no intercepta;

    Una referencia a método es simplemente una notación abreviada para una lambda que solo llama a un método. La usamos cuando mejora la legibilidad: [String::length] en lugar de [s -> s.length()].

void main() {
    // 1 - Function: andThen (primero esta, luego la otra) y compose (primero la otra)
    Function<Integer, Integer> plusOne = x -> x + 1;
    Function<Integer, Integer> timesTwo = x -> x * 2;
    IO.println("plusOne.andThen(timesTwo).apply(5)=" + plusOne.andThen(timesTwo).apply(5));
    IO.println("plusOne.compose(timesTwo).apply(5)=" + plusOne.compose(timesTwo).apply(5));
    // una cadena de procesamiento construida a partir de una lista de funciones
    List<UnaryOperator<String>> steps =
            List.of(String::strip, String::toLowerCase, s -> s.replace(' ', '-'));
    Function<String, String> normalize = Function.identity();
    for (UnaryOperator<String> step : steps) {
        normalize = normalize.andThen(step);
    }
    IO.println("normalize(\"  My Nice Title \")=" + normalize.apply("  My Nice Title "));

    // 2 - Predicate: and, or, negate, Predicate.not
    Predicate<String> isShort = s -> s.length() <= 4;
    Predicate<String> startsWithP = s -> s.startsWith("P");
    List<String> firstNames = List.of("Paul", "Mélanie", "Jo", "Sébastien", "Pierre");
    IO.println("short and P: " + filter(firstNames, isShort.and(startsWithP)));
    IO.println("short or P: " + filter(firstNames, isShort.or(startsWithP)));
    IO.println("not short: " + filter(firstNames, isShort.negate()));
    IO.println("not empty: " + filter(List.of("a", "", "b"), Predicate.not(String::isEmpty)));

    // 3 - Consumer: andThen encadena dos procesamientos sobre el mismo valor
    List<String> log = new ArrayList<>();
    Consumer<String> display = s -> IO.println("display: " + s);
    Consumer<String> remember = log::add;
    Consumer<String> both = display.andThen(remember);
    both.accept("first");
    both.accept("second");
    IO.println("log: " + log);

    // 4 - Comparator: comparing, thenComparing, reversed
    List<Person> persons = new ArrayList<>(List.of(new Person("Paul", 32),
            new Person("Mélanie", 25), new Person("Jo", 32), new Person("Sébastien", 25)));
    persons.sort(Comparator.comparing(Person::age).thenComparing(Person::name));
    IO.println("by age then name: " + persons);
    persons.sort(Comparator.comparingInt(Person::age).reversed()
            .thenComparing(Person::name, Comparator.reverseOrder()));
    IO.println("by descending age then descending name: " + persons);
    // BinaryOperator.minBy construye una función a partir de un comparador
    BinaryOperator<Person> youngest = BinaryOperator.minBy(Comparator.comparingInt(Person::age));
    IO.println("youngest(Paul, Mélanie)=" + youngest.apply(persons.get(0), persons.get(3)));
}

static <T> List<T> filter(List<T> elements, Predicate<? super T> predicate) {
    List<T> result = new ArrayList<>();
    for (T element : elements) {
        if (predicate.test(element)) {
            result.add(element);
        }
    }
    return result;
}

Al exigir que las variables permanezcan sin cambios, Java evita estas situaciones; cuando un estado compartido y mutable es realmente necesario, se hace explícito mediante un objeto ([AtomicInteger], colección…) cuyo comportamiento con respecto a los hilos está especificado.

Un [Supplier<List<TaxBracket>>] habría bastado técnicamente, pero habría sido mucho menos descriptivo. Por ello reservamos las interfaces funcionales para comportamientos breves y puntuales (un criterio, una transformación, una acción), y las interfaces «de negocio» para los roles de la aplicación, sin importar el número de métodos que contengan.

    7.5. Manejo de eventos

    7.5.1. El modelo de oyentes

    Las interfaces funcionales se utilizan para configurar eventos. Java no tiene una palabra clave dedicada para los eventos: utiliza un conjunto de convenciones, conocido como el «modelo de oyentes» (listener model), establecido desde Java 1.1 para los componentes gráficos y los JavaBeans. Una clase [C1] que quiere señalar un evento [Xxx] procede de la siguiente manera:

    • Una clase [XxxEvent], derivada de [java.util.EventObject], encapsula la información del evento. [EventObject] almacena el objeto que desencadenó el evento, denominado origen (source), que se obtiene mediante [getSource()];
    • una interfaz [XxxListener], que extiende la interfaz vacía [java.util.EventListener] (un simple marcador), define el o los métodos que se llamarán cuando ocurra el evento. Con un solo método, es una interfaz funcional: un oyente puede ser una lambda;
    • La clase [C1] administra una lista de oyentes y ofrece dos métodos públicos para suscribirse a ella y cancelar la suscripción: [addXxxListener(XxxListener l)] y [removeXxxListener(XxxListener l)];
    • Cuando una instancia [c1] de [C1] quiere señalar el evento, crea un objeto [XxxEvent] y llama al método de cada oyente registrado, pasándole este objeto. Por convención, esta notificación la realiza un método protegido [fireXxx(XxxEvent e)] («fire», disparar), que una clase derivada puede redefinir para modificar la forma en que se publica el evento;
    • si un objeto [c2] quiere ser notificado del evento [Xxx] del objeto [c1], se registra mediante [c1.addXxxListener(...)]. Puede cancelar su suscripción mediante [c1.removeXxxListener(...)] cuando ya no desee ser notificado. Dado que [c1] administra una lista, distintos objetos pueden suscribirse para ser notificados del mismo evento.

    En este esquema, tenemos:

    • una clase que señala (también se dice «publica» o «emite») un evento;
    • objetos que son notificados de este evento. Se dice que se suscriben o se registran al evento: son los oyentes, o manejadores de eventos;
    • una interfaz de oyente que define la firma de los métodos que serán notificados del evento.

    Este es el patrón de diseño Observer: el emisor no conoce a sus suscriptores; simplemente los notifica. Este modelo ofrece la misma protección que una palabra clave dedicada: la lista de oyentes es un campo privado del emisor. Desde el exterior, solo se puede suscribir o cancelar la suscripción; no se puede vaciar la lista, reemplazar a otros oyentes ni desencadenar el evento en lugar del emisor.

            IO.println("Subscriber [%s]: unsubscribed after %d alert(s)".formatted(name, nbAlerts));
        }
    }
}

    Comentarios:

    • líneas 4–6: cada suscriptor se identifica por un nombre y se le asigna el número máximo de alertas que acepta ([nbAlertsMax]);
    • línea 10: el oyente del suscriptor es una referencia a su método privado [evtTemperatureTooHigh]. Vimos con [Lambdas04.java] que dos evaluaciones de [this::evtTemperatureTooHigh] producen dos objetos diferentes. Si escribiéramos [emitter.addTemperatureTooHighListener(this::evtTemperatureTooHigh)] en [subscribe] y luego [emitter.removeTemperatureTooHighListener(this::evtTemperatureTooHigh)] en [unsubscribe], la cancelación de la suscripción no eliminaría nada, ¡y no se mostraría ningún mensaje de error! Por eso creamos el oyente una sola vez y lo almacenamos en un campo;
    • líneas 18–20: suscripción a un emisor. Es responsabilidad del suscriptor; el suscriptor sabe qué objeto debe eliminar para cancelar su suscripción;
    • líneas 23–25: la cancelación de la suscripción elimina el mismo objeto, [listener]. Cada suscriptor tiene su propio objeto, [listener]: [remove] elimina únicamente el que pertenece al suscriptor en cuestión;
    • línea 28: el manejador del evento. Tiene la forma especificada por la interfaz [TemperatureTooHighListener]. Es privado: solo el suscriptor puede registrarlo en un emisor. Otro enfoque muy común consiste en que la propia clase [Subscriber] ([class Subscriber implements TemperatureTooHighListener]) implemente la interfaz del oyente y se registre con [this]. El inconveniente de este enfoque es que hace público el método [temperatureTooHigh], que cualquiera podría entonces llamar;
    • línea 29: gracias a la redefinición de [getSource], el origen del evento es directamente de tipo [Emitter];
    • líneas 30–31: el manejador muestra el nombre del suscriptor, el nombre del emisor que señaló el evento y la temperatura que lo desencadenó. El formato [%.1f] muestra el número real con un decimal, aquí con punto decimal;
    • Líneas 33–37: tras [nbAlertsMax] alertas, el suscriptor cancela su suscripción al emisor. El suscriptor lo hace durante la notificación del evento, desde su propio manejador; es decir, mientras el método [fireTemperatureTooHigh] recorre la lista de oyentes. Esto es seguro gracias a [CopyOnWriteArrayList]: [remove] crea un nuevo arreglo, pero la iteración en curso continúa sobre el anterior.

void main() {
    var thermometer = new Thermometer("living room");

class Thermometer {
    // la gestión de los oyentes se delega en un objeto PropertyChangeSupport
    private final PropertyChangeSupport changes = new PropertyChangeSupport(this);
    private String name;
    private double temperature;

    Thermometer(String name) {
        this.name = name;
    }

    String getName() {
        return name;
    }

    void setName(String name) {
        String old = this.name;
        this.name = name;
        changes.firePropertyChange("name", old, name);
    }

    double getTemperature() {
        return temperature;
    }

    void setTemperature(double temperature) {
        double old = this.temperature;
        this.temperature = temperature;
        changes.firePropertyChange("temperature", old, temperature);
    }

    // registro y baja de los oyentes
    void addPropertyChangeListener(PropertyChangeListener listener) {
        changes.addPropertyChangeListener(listener);
    }

    void addPropertyChangeListener(String property, PropertyChangeListener listener) {
        changes.addPropertyChangeListener(property, listener);
    }

    void removePropertyChangeListener(PropertyChangeListener listener) {
        changes.removePropertyChangeListener(listener);
    }

    int getNbListeners() {
        return changes.getPropertyChangeListeners().length;
    }
}

    // lambdas y la API Stream

void main() {
    List<Integer> numbers = List.of(3, 8, 1, 6, 5, 4, 9, 2);

    // 1 - filter y map esperan un Predicate<T> y una Function<T, R>
    Predicate<Integer> isEven = n -> n % 2 == 0;
    Function<Integer, Integer> square = n -> n * n;
    List<Integer> evenSquares = numbers.stream().filter(isEven).map(square).toList();
    IO.println("Stream: " + evenSquares);

    // 2 - nuestro propio método de filtrado, llamado con una lambda y luego con una referencia a método
    IO.println("filter(n > 4): " + Tools.filter(numbers, n -> n > 4));
    IO.println("filter(isOdd): " + Tools.filter(numbers, Tools::isOdd));

    // 3 - la ejecución es diferida: el predicado solo se invoca en la operación terminal
    Stream<Integer> large = numbers.stream().filter(n -> {
        IO.print("[test " + n + "] ");
        return n > 7;
    });
    IO.println("the stream is defined, nothing has been executed yet");
    large.forEach(n -> IO.print("-> " + n + " "));
    IO.println();

    // 4 - nuestras propias operaciones intermedias con gatherers (Gatherer, Java 24)
    List<String> cities = List.of("Angers", "Paris", "Lyon", "Nantes", "Aix");
    List<String> result = cities.stream()
            .gather(Tools.filter(v -> v.length() <= 5))
            .gather(Tools.transform(String::toUpperCase))
            .toList();
    IO.println("gatherers: " + result);
}

class Tools {
    // filtra una lista con un predicado: el trabajo que realiza filter
    static <T> List<T> filter(List<T> source, Predicate<? super T> predicate) {
        List<T> result = new ArrayList<>();
        for (T element : source) {
            if (predicate.test(element)) {
                result.add(element);
            }
        }
        return result;
    }

    static boolean isOdd(int n) {
        return n % 2 != 0;
    }

    // una operación intermedia de stream que solo deja pasar los elementos que cumplen el predicado
    static <T> Gatherer<T, ?, T> filter(Predicate<? super T> predicate) {
        return Gatherer.of((_, element, downstream) -> !predicate.test(element) || downstream.push(element));
    }

    // una operación intermedia que transforma cada elemento: el equivalente de map
    static <T, R> Gatherer<T, ?, R> transform(Function<? super T, ? extends R> transformation) {
        return Gatherer.of((_, element, downstream) -> downstream.push(transformation.apply(element)));
    }
}

Solo cuando la operación terminal [forEach] (línea 22) solicita los elementos se ejecuta el predicado, y las evaluaciones se alternan con las salidas de [forEach]: cada elemento recorre todo el flujo antes de que entre el siguiente. Esta es la ejecución diferida (o perezosa) de los streams. Nuestro método [filter], en cambio, construye toda la lista de resultados antes de devolverla;
    • líneas 51–58: para escribir nuestras propias operaciones intermedias (que son perezosas, como las de la API Stream) utilizamos los recolectores intermedios ([Gatherer], Java 24), que son los equivalentes, para las operaciones intermedias, de los recolectores ([Collector]) utilizados por [collect]. [Gatherer.of] recibe una lambda con tres parámetros, llamada por cada elemento del flujo: un estado (innecesario aquí, de ahí el parámetro anónimo [_]), el elemento y la siguiente etapa del flujo ([downstream]), a la que se le pasa un elemento mediante [downstream.push(...)]. La lambda devuelve [false] para detener el flujo; nuestras funciones nunca lo deciden por sí mismas: devuelven el resultado de [push], que es igual a [false] solo si el componente siguiente ya no desea más elementos (o [true] cuando el filtro descarta un elemento). El filtro (línea 52) transmite solo los elementos que cumplen el predicado; la transformación (línea 57) transmite el resultado de la función aplicada a cada elemento;
    • línea 56: [transform] es doblemente genérico: [T] es el tipo de los elementos recibidos, y [R] es el tipo de los elementos producidos. El parámetro [Function<? super T, ? extends R>] sigue la regla que ya vimos: la función consume [T] y produce [R];
    • líneas 27–30: el método de stream [gather] inserta nuestras operaciones en la cadena, que se escribe de la misma manera que para las operaciones de la API Stream: conservamos las ciudades con hasta 5 letras y luego las ponemos en mayúsculas.

    Toda la API Stream está construida sobre este modelo: operaciones que reciben interfaces funcionales y producen nuevos streams, cuyos elementos se calculan solo cuando la operación terminal los solicita.

    7.7. Árboles de expresión

    Algunos lenguajes, como C#, permiten convertir una lambda no en código ejecutable, sino en una estructura de datos que la describe (un «árbol de expresión»): un programa puede entonces analizar la lambda [t -> t.getLimit() > 20000] y traducirla, por ejemplo, a una cláusula SQL [WHERE limits > 20000] ejecutada por el servidor de base de datos.

    Java no tiene un equivalente. Una lambda de Java siempre se compila a código ejecutable: se puede llamar, pero no se puede examinar lo que hace. Por ello, las bibliotecas de acceso a bases de datos recurren a otros medios para expresar una consulta. Hibernate, que veremos en el capítulo 11, ofrece dos soluciones: un lenguaje de consulta similar a SQL pero expresado en términos de clases y propiedades, HQL (["from Bracket t where t.limit > 20000"]), y la API Criteria de Jakarta Persistence, que construye la consulta mediante llamadas a métodos ([cb.gt(t.get("limit"), 20000)]). En ambos casos, la consulta son datos (una cadena o un árbol de objetos) que Hibernate traduce a SQL, mientras que una lambda pasada a [filter] se ejecuta dentro del programa Java.

    7.8. Conclusión

    Puntos clave de este capítulo:

    • Una interfaz funcional es una interfaz que tiene un único método abstracto. Las interfaces predefinidas del paquete [java.util.function] ([Function], [Supplier], [Consumer], [Predicate], sus variantes de dos parámetros y sus versiones primitivas), junto con [Runnable], [Callable] y [Comparator], suelen eliminar la necesidad de definir interfaces propias; cuando se define una, se anota con [@FunctionalInterface];
    • Una interfaz funcional puede ser implementada por una clase (con nombre o anónima), por una expresión lambda o por una referencia a un método ([Class::staticMethod], [object::method], [Class::instanceMethod], [Class::new]). Una lambda no tiene un tipo propio: lo determina el tipo de destino;
    • Las lambdas capturan las variables locales que las rodean, siempre que esas variables sean efectivamente finales; el estado mutable se maneja mediante un objeto o un campo;
    • los métodos [andThen], [compose], [and], [negate], [comparing], [thenComparing]… construyen nuevas funciones a partir de otras existentes;
    • En Java, una lambda es una instancia de una interfaz: se elige una interfaz funcional para un comportamiento breve y puntual, mientras que se elige una interfaz con varios métodos (o una interfaz «de negocio») para un rol de la aplicación;
    • Un evento se configura mediante el patrón de oyentes: una clase [XxxEvent] derivada de [EventObject], una interfaz [XxxListener], métodos [addXxxListener] / [removeXxxListener], y una lista de oyentes ([CopyOnWriteArrayList]) recorrida por un método [fireXxx]. Para cancelar la suscripción de un oyente, hay que conservar el objeto suscrito. [PropertyChangeSupport] proporciona este mecanismo listo para usar para los cambios de propiedades;
    • la API Stream se basa en operaciones que aceptan interfaces funcionales; Java no tiene árboles de expresión, y Hibernate expresa sus consultas en HQL o mediante la API Criteria.

    Las lambdas reaparecerán en todos los capítulos siguientes: un hilo ejecuta un [Runnable], y un [ExecutorService] ejecuta un [Callable] (capítulo 8), un [CompletableFuture] encadena funciones (capítulo 9), y los servicios web de Spring Boot manejan las solicitudes HTTP en métodos que el framework invoca como oyentes (capítulo 13).
