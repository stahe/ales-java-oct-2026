    10. Acceso a bases de datos con JDBC

    Requisitos previos: la versión 6 de la aplicación [Tax], descrita al final de este capítulo, reutiliza los módulos [tax-dao], [tax-business] y [tax-ui] de la versión 5 (capítulo 6). Antes de compilar o abrir sus proyectos, debe haber instalado la versión 5 en el repositorio Maven local mediante el comando [mvn install] ejecutado en la carpeta [06-architectures/TaxV5] (consulte el capítulo 6, sección sobre [mvn install]).

    10.1. El controlador JDBC

    Retomemos la arquitectura en capas utilizada en varias ocasiones desde el capítulo 6. Hasta ahora, la capa [dao] de la aplicación [Tax] ha utilizado tres tipos de fuentes de datos:

    • datos codificados directamente en el código ([HardwiredTax]);
    • datos de un archivo de texto ([FileTax]);
    • datos de un archivo JSON ([JsonTax]).

    En este capítulo examinamos el caso en que los datos provienen de una base de datos. La arquitectura queda así:

    En el diagrama anterior, la capa [dao] [1] se comunica con el SGBD (sistema de gestión de bases de datos) [3], que administra la base de datos [4], a través de una biblioteca de clases [2] específica del SGBD utilizado. Esta biblioteca implementa una API estándar de la plataforma Java, JDBC («Java DataBase Connectivity»), que forma parte del JDK desde la versión 1.1, en 1997. Se denomina controlador JDBC («JDBC driver»). Todos los SGBD habituales disponen de un controlador JDBC, distribuido como un archivo [.jar].

    JDBC es, ante todo, un conjunto de interfaces, definidas en los paquetes [java.sql] y [javax.sql] del módulo [java.sql] del JDK: [Connection], [Statement], [PreparedStatement], [ResultSet], [DataSource]… Un controlador JDBC proporciona clases que implementan estas interfaces. El código de la aplicación, en cambio, solo interactúa con las interfaces: en general no contiene los nombres de las clases del controlador. Esto difiere de otras plataformas, donde el código suele usar directamente las clases propias de cada SGBD ([MySqlConnection], [SqlConnection]…): en Java, la abstracción ha sido la norma desde el principio, y cambiar a otro SGBD consiste esencialmente en cambiar el controlador y la dirección de la base de datos, como veremos. Sin embargo, cada SGBD tiene su propio dialecto de SQL: esta independencia tiene sus límites, que también examinaremos.

    Utilizamos un único SGBD, MySQL 8, que el apéndice «El SGBD MySQL con Laragon» instala en Windows, junto con su controlador JDBC oficial, MySQL Connector/J, versión 9.7.0. Las bases de datos se crean mediante scripts SQL ejecutados con el cliente de línea de comandos [mysql]; el apéndice también muestra cómo crearlas con el cliente gráfico HeidiSQL incluido en Laragon.

    10.2. Las dos formas de utilizar una fuente de datos

    Se puede acceder a una base de datos de dos maneras distintas:

    • modo conectado;
    • modo desconectado.

    En el modo conectado, la aplicación:

    • abre una conexión con la fuente de datos;
    • trabaja con la fuente de datos en modo de lectura/escritura;
    • cierra la conexión.

    En el modo desconectado, la aplicación:

    • abre una conexión con la fuente de datos;
    • recupera en memoria una copia de la totalidad o de parte de los datos de la fuente;
    • cierra la conexión;
    • trabaja con la copia de los datos en memoria, leyéndola y modificándola;
    • cuando termina el trabajo, abre una conexión, envía los datos modificados a la fuente de datos para que se actualice y cierra la conexión.

    El modo conectado es el de la interfaz [ResultSet] de JDBC: las filas del resultado de una consulta se leen mientras la conexión está abierta. El modo desconectado es el de la interfaz [CachedRowSet] del paquete [javax.sql.rowset] (Java 5): una tabla en memoria que se llena a partir de una consulta, se modifica sin conexión y luego envía sus cambios a la base de datos. Estos componentes «RowSet» siguen presentes en JDK 25, pero rara vez se utilizan en aplicaciones nuevas: trabajar sobre una copia de los datos en memoria, con guardado posterior de los cambios, corresponde hoy a un ORM («Object-Relational Mapper»), que manipula objetos Java ordinarios en lugar de filas de tablas. El ORM más utilizado en Java, Hibernate, es el tema del capítulo 11. Por ello nos centraremos principalmente en el modo conectado —en el que se basa Hibernate— y mostraremos el modo desconectado solo mediante un ejemplo al final del capítulo.

    10.3.2. Los cuatro comandos básicos del lenguaje SQL

    SQL («Structured Query Language») es un lenguaje parcialmente estandarizado para consultar y actualizar bases de datos. Todos los dialectos de los SGBD respetan la parte estandarizada de SQL, pero agregan al lenguaje extensiones propias que aprovechan sus características específicas. Ya hemos visto dos ejemplos: la generación automática de claves primarias y los tipos de datos permitidos para las columnas de las tablas suelen depender del SGBD.

    Los cuatro comandos básicos del lenguaje SQL que presentamos aquí están estandarizados y son aceptados por todos los SGBD:

    Comando
    Función
    [select col1, col2, … from table1, table2, … where condition order by expression]
    La consulta que sirve para recuperar datos de una base de datos. Solo las palabras clave [select] y [from] son obligatorias. Se realiza una combinación (join) con todas las tablas que siguen a la palabra clave [from]; solo se conservan las columnas que siguen a la palabra clave [select] ; solo se conservan las filas que cumplen la condición de la palabra clave [where] ; las filas resultantes, ordenadas según la expresión de la palabra clave [order by], forman el resultado de la consulta. Este resultado es una tabla.
    [insert into table(col1, col2, …) values (val1, val2, …)]
    Inserta una fila en [table]. [(col1, col2, …)] especifica las columnas de la fila que se inicializan con los valores [(val1, val2, …)].
    [update table set col1=val1, col2=val2, … where condition]
    Actualiza las filas de [table] según [condition] (todas las filas si no hay [where]). En esas filas, la columna [coli] toma el valor [vali].
    [delete from table where condition]
    Elimina todas las filas de [table] que cumplen [condition] (todas las filas si no hay [where]).

    10.3.3. Las interfaces básicas de JDBC para el modo conectado

    Volvamos al diagrama de una aplicación que accede a una base de datos a través de un controlador JDBC:

    En el modo conectado, la aplicación:

    • abre una conexión con la fuente de datos;
    • trabaja con la fuente de datos en modo de lectura/escritura;
    • cierra la conexión.

    En estas operaciones intervienen principalmente tres tipos de objetos:

    • la conexión ([Connection]), que encapsula las propiedades y los métodos de la conexión con la base de datos;
    • el comando SQL ([Statement], o [PreparedStatement] para un comando parametrizado), que encapsula las propiedades y los métodos del comando SQL ejecutado;
    • el resultado ([ResultSet]), que encapsula las propiedades y los métodos del resultado de un comando SQL [select].

    Son interfaces del paquete [java.sql]. El controlador de MySQL las implementa mediante clases de sus propios paquetes ([com.mysql.cj.jdbc.ConnectionImpl], [ClientPreparedStatement], [ResultSetImpl]…), que la aplicación no necesita conocer: obtiene sus objetos mediante métodos que devuelven interfaces. La conexión se obtiene de la clase [DriverManager] (o de una fuente de datos [DataSource], de la que hablaremos más adelante), el comando SQL lo crea la conexión y el resultado lo devuelve el comando SQL.

    10.3.3.1. La interfaz Connection

    Sirve para administrar la conexión con la base de datos. Una conexión se obtiene mediante el método estático [DriverManager.getConnection(url, user, password)], que recibe la URL de la base de datos y JDBC —por ejemplo, [jdbc:mysql://localhost:3306/dbarticles]— y las credenciales del usuario. La conexión devuelta ya está abierta. Los métodos de la interfaz [Connection] que utilizaremos son los siguientes:

    Método
    Función
    [createStatement]
    Crea un comando SQL asociado a esta conexión.
    [prepareStatement]
    [prepareStatement(sql)] crea un comando SQL configurado como [PreparedStatement] asociado a esta conexión.
    [prepareCall]
    [prepareCall("{call name(?, ?)}")] crea un comando [CallableStatement] que ejecuta un procedimiento almacenado en la base de datos.
    [setAutoCommit]
    [setAutoCommit(false)] inicia una transacción (véase más adelante).
    [commit], [rollback]
    confirma o revierte la transacción actual.
    [getMetaData]
    devuelve un objeto [DatabaseMetaData] que describe el SGBD y el controlador.
    [isValid]
    [isValid(seconds)] comprueba que la conexión sigue siendo utilizable.
    [close]
    cierra la conexión, junto con los comandos SQL y los resultados que produjeron.

    10.3.3.2. La interfaz Statement

    Sirve para ejecutar un comando SQL. Los métodos de esta interfaz que utilizaremos son los siguientes:

    Método
    Función
    [executeQuery]
    [executeQuery(sql)] ejecuta un comando SQL [select]. Produce un objeto [ResultSet] que representa el resultado de [select].
    [executeUpdate]
    [executeUpdate(sql)] ejecuta un comando SQL [update], [insert], [delete] (o un comando de definición como [create table]). Devuelve el número de filas afectadas por la operación (actualizadas, insertadas, eliminadas). [executeLargeUpdate] (Java 8) devuelve este número en forma de [long].
    [execute]
    [execute(sql)] ejecuta cualquier comando SQL. Devuelve [true] si el comando produjo un [ResultSet], que se obtiene entonces mediante [getResultSet], [false] si produjo un número de filas, que se obtiene mediante [getUpdateCount].
    [addBatch], [executeBatch]
    agregan un comando a un lote y ejecutan el lote (véase más adelante).
    [getGeneratedKeys]
    devuelve las claves primarias generadas por el SGBD durante una ejecución de [insert].
    [setQueryTimeout]
    [setQueryTimeout(seconds)] establece el tiempo máximo de ejecución del comando.
    [close]
    cierra el comando SQL, así como su [ResultSet].

    10.3.3.3. La interfaz ResultSet

    Encapsula los resultados de un comando SQL [select]. Un objeto [ResultSet] representa una tabla con filas y columnas, que se procesa de forma secuencial: primero la primera fila, luego la segunda, y así sucesivamente, sin posibilidad de retroceder (este es el tipo predeterminado, [TYPE_FORWARD_ONLY]; JDBC también admite resultados que se pueden recorrer en ambos sentidos, pero se usan muy poco). El [ResultSet] tiene un cursor posicionado inicialmente antes de la primera fila: hay que llamar a [next] para leer la primera fila. Los métodos de esta interfaz que utilizaremos son los siguientes:

    Método
    Función
    [next]
    Pasa a la siguiente fila de la tabla de resultados. Devuelve [true] si la fila se leyó correctamente y [false] si no quedan más filas.
    [getInt]
    [getInt(i)] devuelve el valor entero de la columna número i de la fila actual. Las columnas se numeran a partir de 1, no de 0. [getInt("name")] devuelve el valor de la columna llamada [name]. Otros métodos similares son [getBoolean], [getBigDecimal], [getDouble], [getLong], [getString]…
    [getObject]
    [getObject(i)] devuelve el valor de la columna i en forma de [Object], del tipo elegido por el controlador; [getObject(i, LocalDate.class)] (Java 7) lo devuelve en el tipo solicitado.
    [wasNull]
    devuelve [true] si la última columna leída no tenía valor, lo que se representa con el valor SQL [NULL]. Los métodos que devuelven un objeto ([getString], [getBigDecimal], [getObject]…) devuelven entonces [null]; los que devuelven un tipo primitivo ([getInt], [getDouble]…) devuelven 0: solo [wasNull] permite distinguir 0 de [NULL].
    [getMetaData]
    devuelve un objeto [ResultSetMetaData] que describe las columnas del resultado: [getColumnCount] (el número de columnas), [getColumnLabel(i)] (el nombre de la columna n.º i), [getColumnTypeName(i)] (su tipo SQL)…
    [close]
    cierra el resultado.

    10.3.4. Manejo de errores

    La capa [dao] puede encontrar numerosos errores al operar la base de datos: servidor caído, base de datos inexistente, contraseña incorrecta, error de sintaxis SQL, violación de una restricción de integridad, etc. Se notifican como excepciones [SQLException]. [SQLException] es una excepción verificada (checked) (capítulo 3): todos los métodos de JDBC la declaran en su cláusula [throws], y el compilador exige que el código que los llama la capture o la declare a su vez. El código de la capa [dao] debe tratar estos errores y, en cualquier caso, liberar los recursos que ha adquirido: la conexión, el comando SQL y el resultado deben cerrarse.     Una nota histórica: hasta Java 5, había que cargar la clase del controlador antes de abrir una conexión, mediante una instrucción como [Class.forName("com.mysql.jdbc.Driver")], que todavía se encuentra en muchos ejemplos de Internet. Desde Java 6 (JDBC 4.0), esto ya no es necesario: cada archivo de controlador declara su clase en un archivo [META-INF/services/java.sql.Driver], y [DriverManager] carga automáticamente todos los controladores presentes en el classpath mediante el mecanismo de servicios ([ServiceLoader]).

    10.3.7. Ejecución de una consulta SELECT

    La ejecución de comandos SQL comprende los siguientes pasos:

    • conectarse a la base de datos;
    • enviar los comandos SQL a la base de datos;
    • procesar los resultados de los comandos SQL;
    • cerrar la conexión.

    Los pasos 2 y 3 pueden repetirse; la conexión se cierra solo al final del procesamiento de la base de datos. Las conexiones abiertas son recursos limitados en un SGBD: hay que economizarlas y siempre se procura limitar la duración de una conexión abierta. En nuestro programa, la conexión se cierra después de cada comando SQL y se abre una nueva para el comando siguiente.

    Sin embargo, abrir una conexión es costoso: requiere establecer una conexión de red con el servidor, posiblemente negociar el cifrado y autenticarse. [DriverManager] no hace nada para reducir este costo: cada llamada a [getConnection] abre una nueva conexión de red, y cada [close] la cierra realmente. Para una herramienta interactiva como esta, no es un problema. Una aplicación que ejecuta muchos comandos SQL —un servidor web, por ejemplo— utiliza en cambio un pool de conexiones: cuando la aplicación cierra una conexión, el pool no la cierra realmente, sino que la devuelve al pool; cuando la aplicación solicita una nueva conexión, recibe una de las conexiones del pool que ya están establecidas. La ventaja de este sistema es que es transparente para el desarrollador: el código que abre y cierra conexiones mediante un bloque try-with-resources no necesita modificarse. Veremos cómo utilizarlo en la sección «Fuentes de datos y pools de conexiones». Abrir una conexión al comienzo de cada operación y cerrarla al final es, por lo tanto, la mejor práctica.

    private static void executeSelect(String url, String user, String password, String query) {
        // la conexión, la sentencia SQL y el resultado se cerrarán al salir del try, en orden inverso
        try (Connection connection = DriverManager.getConnection(url, user, password);

    private static void displayResultSet(ResultSet result) throws SQLException {
        // los nombres de las columnas, dados por los metadatos del resultado
        ResultSetMetaData metadata = result.getMetaData();
        int nbColumns = metadata.getColumnCount();
        String[] names = new String[nbColumns];
        for (int i = 1; i <= nbColumns; i++) {
            names[i - 1] = metadata.getColumnLabel(i);
        }
        String header = String.join(",", names);
        String dashes = "-".repeat(header.length());
        IO.println("\n" + dashes + "\n" + header + "\n" + dashes + "\n");
        // las filas, una tras otra
        while (result.next()) {
            StringBuilder row = new StringBuilder();
            for (int i = 1; i <= nbColumns; i++) {
                row.append(result.getObject(i)).append(' ');
            }
            IO.println(row);
        }
    }

    10.4.2. Fuentes de datos y pools de conexiones

    [DriverManager] es la forma tradicional de obtener una conexión. Desde JDBC 2.0, las aplicaciones prefieren utilizar una fuente de datos —un objeto que implementa la interfaz [javax.sql.DataSource]—. Una fuente de datos se configura una sola vez (URL, nombre de usuario, contraseña, ajustes del controlador) y luego proporciona conexiones mediante su método [getConnection()], sin ningún parámetro. El código que utiliza la fuente de datos desconoce tanto la URL como las credenciales: en una aplicación, es la propia fuente de datos la que se registra en el contenedor de inyección de dependencias (capítulo 6), y no los parámetros de conexión. Hay dos grandes familias de fuentes de datos:

    • las proporcionadas por los controladores, como [com.mysql.cj.jdbc.MysqlDataSource] para MySQL. Al igual que [DriverManager], abren una nueva conexión de red cada vez que se llama a [getConnection];
    • las que administran un pool de conexiones. La más utilizada es HikariCP, el pool de conexiones predeterminado de Spring Boot. Su [getConnection] devuelve una conexión del pool, y el [close] de esa conexión la devuelve al pool en lugar de cerrarla.

    La segunda parte del programa [Jdbc03] compara ambas (líneas 41–56 y 75–90 del programa anterior):

    • líneas 42–45: una fuente de datos [MysqlDataSource], configurada mediante sus métodos [setURL], [setUser] y [setPassword]. Es la única parte del programa que hace referencia a una clase del controlador de MySQL;
    • línea 46: el método [measure] recibe la fuente de datos con el tipo de la interfaz [DataSource]: serviría para cualquier controlador;

    10.4.3. ¿Qué nivel de abstracción elegir?

    La independencia de JDBC respecto del SGBD parece ideal. En la práctica, JDBC no puede ocultar todas las características específicas de un SGBD:

    • el propio SQL difiere de un SGBD a otro en cuanto se va más allá de las operaciones básicas: generación de claves primarias, limitación del número de filas devueltas ([limit 10] en MySQL y PostgreSQL, [top 10] o [offset … fetch] en SQL Server), tipos de columnas, funciones de fecha, etc.;
    • los tipos Java devueltos por [getObject] pueden variar: veremos que [count(*)] de MySQL devuelve un [Long];
    • los códigos de error ([getErrorCode]) son específicos de cada SGBD, y los códigos SQLSTATE no siempre se usan de la misma manera;
    • la URL y los parámetros de configuración son específicos de cada controlador.

    Los parámetros de las consultas, en cambio, son uniformes: JDBC impone la notación [?] (parámetros posicionales, sin nombre), que cada controlador traduce a la sintaxis de su SGBD.

    Para superar estas limitaciones o simplificar la escritura del código JDBC, hoy se utiliza principalmente lo siguiente:

    • un ORM —casi siempre Hibernate, como se verá en el capítulo 11—, donde la capa [dao] manipula objetos Java y escribe sus consultas en HQL, un lenguaje de consulta orientado a objetos; Hibernate genera el SQL específico de cada SGBD (su «dialecto»);
    • bibliotecas que conservan el SQL pero eliminan el código repetitivo de JDBC: [JdbcTemplate] y [JdbcClient] de Spring (este último desde Spring Framework 6.1), que transforman directamente filas de [select] en objetos Java y convierten [SQLException] en excepciones no verificadas; jOOQ, que construye consultas SQL en Java con validación en tiempo de compilación; MyBatis, que asocia consultas SQL escritas en archivos XML o en anotaciones con métodos Java.

    Todas estas herramientas se basan en JDBC: comprender JDBC sigue siendo útil para entender lo que hacen y diagnosticar sus problemas.

        String query = "insert into articles(name, price, currentstock, minimumstock) values(?, ?, ?, ?)";
        try (Connection connection = DriverManager.getConnection(URL, USER, PASSWORD);

            return statement.executeUpdate(query);
        }

    10.6. Transacciones

    10.6.1. Información general

    Una transacción es una secuencia de comandos SQL ejecutados “de forma atómica”:

    • o bien todas las operaciones tienen éxito;
    • o bien una de ellas falla, en cuyo caso se revierten todas las operaciones anteriores.

    En definitiva, o bien todas las operaciones de una transacción se aplican con éxito, o bien no se aplica ninguna. El ejemplo clásico es una transferencia bancaria: el débito de una cuenta y el crédito en otra deben completarse ambos o ninguno. Cuando la propia aplicación controla la transacción, la confirma con un comando [COMMIT] o la revierte con un comando [ROLLBACK].

    En nuestros ejemplos anteriores no usamos ninguna transacción. Y sin embargo había transacciones, porque en un SGBD un comando SQL siempre se ejecuta dentro de una transacción. Si la aplicación no inicia por sí misma una transacción explícita, el SGBD utiliza una transacción implícita. Hay entonces dos casos:

    • cada comando SQL forma parte de una transacción, abierta por el SGBD antes del comando y confirmada después. Esto se denomina modo autocommit. Se comporta como si la aplicación creara una transacción para cada comando SQL;
    • el SGBD no está en modo autocommit: inicia una transacción implícita con el primer comando SQL emitido fuera de una transacción y deja que la aplicación la finalice. Todos los comandos SQL siguientes forman parte de esta transacción implícita, que puede terminar por diversos eventos (cierre de la conexión, inicio de una nueva transacción, etc.), según reglas propias de cada SGBD. Conviene evitar este modo.

    JDBC impone el primer caso: una conexión JDBC está en modo autocommit al abrirse, sea cual sea la configuración del SGBD (MySQL, con el motor de almacenamiento InnoDB usado de forma predeterminada, también está en modo autocommit).

    Los comandos SQL de distintos usuarios se ejecutan simultáneamente, dentro de transacciones que se ejecutan en paralelo. Las operaciones realizadas por una transacción pueden afectar a las realizadas por otra. Existen cuatro niveles de aislamiento entre transacciones de distintos usuarios:

    • Read Uncommitted;
    • Read Committed;
    • Repeatable Read;
    • Serializable.

    Read Uncommitted

    Este nivel de aislamiento también se conoce como “Dirty Read” (lectura sucia). Este es un ejemplo de lo que puede ocurrir en este modo:

    • un usuario llamado U1 inicia una transacción sobre la tabla T;
    • un usuario llamado U2 inicia una transacción sobre la misma tabla T;
    • el usuario U1 modifica filas de la tabla T pero aún no ha confirmado los cambios;
    • el usuario U2 “ve” estos cambios y toma decisiones basándose en lo que ve;
    • el usuario U1 revierte su transacción con [ROLLBACK].

    En el paso 4, el usuario U2 tomó una decisión basándose en datos que luego resultaron ser incorrectos.

    Read Committed

    Este nivel de aislamiento evita el problema anterior: en el paso 4, el usuario U2 no “ve” los cambios realizados por el usuario U1 en la tabla T. Solo los verá después de que U1 haya confirmado su transacción con un [COMMIT]. Sin embargo, en este modo puede darse la siguiente situación:

    • un usuario U1 inicia una transacción sobre la tabla T;
    • un usuario U2 inicia una transacción sobre la misma tabla T;
    • el usuario U2 ejecuta un [select] para calcular el promedio de la columna C de las filas de T que cumplen cierta condición;
    • el usuario U1 modifica ([update]) ciertos valores de la columna C de T y confirma los cambios ([commit]);
    • el usuario U2 repite el mismo [select] del paso 3. Descubre que el promedio de la columna C ha cambiado debido a las modificaciones realizadas por U1.

    El usuario U2 ahora ve solo los cambios confirmados por U1, pero, aun dentro de la misma transacción, dos operaciones idénticas producen resultados distintos. Esta situación se denomina “lectura no repetible”. Es problemática para quien desea una vista coherente de la tabla T.

    Repeatable Read

    En este nivel de aislamiento, a un usuario se le garantiza obtener los mismos resultados en las lecturas de la base de datos mientras permanezca dentro de la misma transacción. Trabaja sobre una “instantánea” de los datos que no refleja los cambios realizados por otras transacciones, aunque estos hayan sido confirmados. Solo verá esos cambios una vez que haya finalizado su propia transacción.

    Este nivel de aislamiento aún no es perfecto en teoría: otra transacción puede agregar ([insert]) filas que cumplan la condición del paso 3, lo que modificaría el resultado de una lectura posterior. Estas filas se denominan “lecturas fantasma”. Este es el nivel de aislamiento predeterminado de MySQL (InnoDB), que además evita las lecturas fantasma en las lecturas simples.

    Serializable

    En este modo de aislamiento, las transacciones están completamente aisladas entre sí: el resultado de dos transacciones ejecutadas simultáneamente es el mismo que si se hubieran ejecutado una tras otra. Para lograrlo, el SGBD bloquea los datos leídos y hace que las transacciones que intentan modificarlos esperen (o fallen). Este nivel reduce el paralelismo y, en consecuencia, el rendimiento.

    No todos los SGBD ofrecen los cuatro niveles de aislamiento. El nivel de aislamiento predeterminado suele ser Read Committed (SQL Server, PostgreSQL, Oracle) o Repeatable Read (MySQL). La aplicación puede especificar explícitamente el nivel de aislamiento deseado.

    10.6.2. Gestión de transacciones (API)

    Con JDBC, las transacciones las gestiona la conexión. No existe un objeto “transacción”: una conexión tiene como máximo una transacción activa, y todos los comandos SQL ejecutados en esa conexión forman parte de ella. Los métodos pertinentes de la interfaz [Connection] son los siguientes:

    Método
    Función
    [setAutoCommit]
    [setAutoCommit(false)] sale del modo autocommit: los comandos SQL siguientes forman parte de una transacción, que comienza con el primero de ellos y termina con [commit] o [rollback]. Con el siguiente comando comienza entonces una nueva transacción. [setAutoCommit(true)] vuelve al modo autocommit, confirmando la transacción en curso.
    [commit]
    confirma la transacción: los resultados de los comandos SQL emitidos dentro de la transacción pasan a ser definitivos y visibles para otras transacciones.
    [rollback]
    revierte la transacción: se deshacen los resultados de los comandos SQL emitidos en la transacción.
    [setSavepoint]
    establece un punto de restauración (un objeto [Savepoint]) en la transacción en curso.
    [rollback(Savepoint)]
    revierte los comandos SQL ejecutados desde el punto de restauración, sin revertir los que lo precedieron: la transacción continúa.
    [setTransactionIsolation]
    establece el nivel de aislamiento de las transacciones de la conexión. Debe llamarse antes del inicio de una transacción.

    El nivel de aislamiento es una de las constantes de la interfaz [Connection]:

    Valor
    Significado
    [TRANSACTION_READ_UNCOMMITTED]
    La transacción puede leer datos escritos por otra transacción que esta aún no ha confirmado. Debe evitarse.
    [TRANSACTION_READ_COMMITTED]
    La transacción no puede leer datos escritos por otra transacción que esta aún no ha confirmado. Sin embargo, los datos leídos dos veces seguidas dentro de la transacción pueden cambiar, porque otra transacción pudo haberlos modificado entretanto; otra transacción también pudo haber agregado filas (filas fantasma).
    [TRANSACTION_REPEATABLE_READ]
    Los datos leídos por la transacción no cambian hasta que esta finaliza. En teoría, esto no impide que otra transacción agregue filas.
    [TRANSACTION_SERIALIZABLE]
    Todo se comporta como si la transacción se ejecutara sola. Esto reduce el rendimiento porque las transacciones ya no se ejecutan en paralelo.

    Una conexión que ha salido del modo autocommit debe cerrarse después de que la transacción haya sido confirmada o revertida. Si se cierra mientras hay una transacción en curso, el resultado depende del controlador (MySQL Connector/J la revierte): siempre se debe confirmar explícitamente una transacción.

import java.math.BigDecimal;
import java.sql.Connection;
import java.sql.DriverManager;
import java.sql.PreparedStatement;
import java.sql.ResultSet;
import java.sql.SQLException;
import java.sql.Savepoint;
import java.sql.Statement;
import java.util.List;

// transacciones
public class Jdbc06 {

    private static final String URL = "jdbc:mysql://localhost:3306/dbarticles";
    private static final String USER = "root";
    private static final String PASSWORD = "";

    public static void main(String[] args) {
        IO.println("JDBC URL of the database: [" + URL + "]");

        // dos artículos con el mismo nombre: la restricción de unicidad UNQ_NAME rechazará el segundo
        List<Article> articles = List.of(new Article(0, "article", new BigDecimal("100"), 10, 1),
                new Article(0, "article", new BigDecimal("200"), 20, 2));

        try {
            // 1 - inserción sin transacción explícita
            IO.println("\nInsertion without a transaction...");
            executeUpdate("delete from articles");
            try {
                insertArticlesOutOfTransaction(articles);
            } catch (SQLException ex) {
                IO.println("Database access error (" + ex.getMessage() + ")");
            }
            displayArticles();

            // 2 - lo mismo en una transacción
            IO.println("\nInsertion in a transaction...");
            executeUpdate("delete from articles");
            insertArticlesInTransaction(articles);
            displayArticles();

            // 3 - una transacción con un punto de guardado
            IO.println("\nInsertion in a transaction with a savepoint...");
            executeUpdate("delete from articles");
            insertArticlesWithSavepoint(articles);
            displayArticles();
        } catch (SQLException ex) {
            IO.println("Database access error (" + ex.getMessage() + ")");
        }
    }

    // inserción de una lista de artículos sin transacción explícita (modo autocommit)
    private static void insertArticlesOutOfTransaction(List<Article> articles) throws SQLException {
        try (Connection connection = DriverManager.getConnection(URL, USER, PASSWORD);
             PreparedStatement statement = createInsertStatement(connection)) {
            for (Article article : articles) {
                insertArticle(statement, article);
            }
        }
    }

    // inserción de una lista de artículos en una transacción
    private static void insertArticlesInTransaction(List<Article> articles) throws SQLException {
        try (Connection connection = DriverManager.getConnection(URL, USER, PASSWORD)) {
            // inicio de la transacción: se sale del modo autocommit
            connection.setTransactionIsolation(Connection.TRANSACTION_READ_COMMITTED);
            connection.setAutoCommit(false);
            try (PreparedStatement statement = createInsertStatement(connection)) {
                for (Article article : articles) {
                    insertArticle(statement, article);
                }
                // todo salió bien: la transacción se confirma
                connection.commit();
                IO.println("transaction committed...");
            } catch (SQLException ex) {
                // una inserción falló: la transacción se revierte
                connection.rollback();
                IO.println("transaction rolled back (" + ex.getMessage() + ")");
            }
        }
    }

    // inserción en una transacción: el fallo de una inserción solo cancela lo que sigue
    // al último punto de guardado
    private static void insertArticlesWithSavepoint(List<Article> articles) throws SQLException {
        try (Connection connection = DriverManager.getConnection(URL, USER, PASSWORD)) {
            connection.setAutoCommit(false);
            try (PreparedStatement statement = createInsertStatement(connection)) {
                for (Article article : articles) {
                    // un punto de guardado antes de cada inserción
                    Savepoint beforeInsertion = connection.setSavepoint();
                    try {
                        insertArticle(statement, article);
                    } catch (SQLException ex) {
                        // solo se deshace la inserción fallida
                        connection.rollback(beforeInsertion);
                        IO.println("insertion of [" + article.name() + ", " + article.price() + "] cancelled ("
                                + ex.getMessage() + ")");
                    }
                }
                connection.commit();
                IO.println("transaction committed...");
            } catch (SQLException ex) {
                connection.rollback();
                IO.println("transaction rolled back (" + ex.getMessage() + ")");
            }
        }
    }

    // la sentencia parametrizada que inserta un artículo
    private static PreparedStatement createInsertStatement(Connection connection) throws SQLException {
        return connection.prepareStatement(
                "insert into articles(name, price, currentstock, minimumstock) values(?, ?, ?, ?)");
    }

    // inserción de un artículo con la sentencia parametrizada
    private static void insertArticle(PreparedStatement statement, Article article) throws SQLException {
        statement.setString(1, article.name());
        statement.setBigDecimal(2, article.price());
        statement.setInt(3, article.currentStock());
        statement.setInt(4, article.minimumStock());
        statement.executeUpdate();
        IO.println("article [" + article.name() + ", " + article.price() + "] inserted");
    }

    // ejecución de una sentencia de actualización
    private static void executeUpdate(String query) throws SQLException {
        try (Connection connection = DriverManager.getConnection(URL, USER, PASSWORD);
             Statement statement = connection.createStatement()) {
            IO.println("There were " + statement.executeUpdate(query) + " row(s) modified");
        }
    }

    // visualización del contenido de la tabla
    private static void displayArticles() throws SQLException {
        try (Connection connection = DriverManager.getConnection(URL, USER, PASSWORD);
             Statement statement = connection.createStatement();
             ResultSet result = statement.executeQuery(
                     "select id, name, price, currentstock, minimumstock from articles")) {
            IO.println("Content of the [articles] table:");
            while (result.next()) {
                IO.println("  " + result.getInt(1) + " " + result.getString(2) + " "
                        + result.getBigDecimal(3) + " " + result.getInt(4) + " " + result.getInt(5));
            }
        }
    }
}

            IO.println("Maximum price beyond 10000 euros: " + empty);

            BigDecimal average = singleValue("select avg(price) from articles", BigDecimal.class);
            Integer number = singleValue("select count(id) from articles", Integer.class);
            IO.println("Rounded average = " + average.setScale(2, RoundingMode.HALF_UP)

            // una conversión directa falla: count devuelve un Long y no un Integer
            int n = (int) nbArticles;
            IO.println("n = " + n);
        } catch (SQLException | ClassCastException ex) {
            IO.println(ex.getClass().getSimpleName() + " : " + ex.getMessage());
        }
    }

    // ejecución de un select que devuelve un único valor: primera columna de la primera fila
    // el resultado es null si el select no devuelve ninguna fila o si el valor es NULL de SQL
    private static Object singleValue(String query) throws SQLException {
        try (Connection connection = DriverManager.getConnection(URL, USER, PASSWORD);
             Statement statement = connection.createStatement();
             ResultSet result = statement.executeQuery(query)) {
            return result.next() ? result.getObject(1) : null;
        }
    }

    // lo mismo, con el valor convertido por el controlador al tipo solicitado
    private static <T> T singleValue(String query, Class<T> type) throws SQLException {
        try (Connection connection = DriverManager.getConnection(URL, USER, PASSWORD);
             Statement statement = connection.createStatement();
             ResultSet result = statement.executeQuery(query)) {
            return result.next() ? result.getObject(1, type) : null;
        }
    }

    // el nombre simple de la clase de un objeto
    private static String type(Object object) {
        return object == null ? "null" : object.getClass().getSimpleName();
    }

    10.8. JDBC es bloqueante: hilos virtuales

    El capítulo 9 mostró que las operaciones de E/S no deben bloquear un hilo de la aplicación en aplicaciones que atienden a muchos usuarios (servidores, servicios web): mientras un comando SQL se ejecuta en el servidor, el hilo que lo emitió espera. Sin embargo, JDBC es una API bloqueante: [getConnection], [executeQuery], [next], [commit]… no devuelven el control hasta que el SGBD ha respondido. No existe una versión asíncrona de JDBC: un proyecto de API asíncrona (ADBA) se abandonó en 2019, y la API reactiva R2DBC —que existe fuera del JDK— no reemplazó a JDBC.

    Desde Java 21, la solución de la plataforma Java es el hilo virtual (capítulo 8): un hilo ligero, gestionado por la JVM, del que pueden crearse miles. Cuando un hilo virtual espera una respuesta de la red, la JVM lo aparta y libera el hilo del sistema que lo ejecutaba, lo que permite que este ejecute otro hilo virtual. El código sigue siendo secuencial y bloqueante —sencillo de escribir y de leer—, pero la espera ya no genera sobrecarga. Los controladores JDBC recientes, incluido Connector/J 9, están escritos para funcionar con hilos virtuales, y desde Java 24 (JEP 491), un hilo virtual que espera en un bloque [synchronized] ya no monopoliza el hilo del sistema.

public class Jdbc08 {

    public static void main(String[] args) throws InterruptedException {
        // el origen de datos: un grupo de como máximo 4 conexiones a la base de datos [dbarticles]
        HikariConfig config = new HikariConfig();
        config.setJdbcUrl("jdbc:mysql://localhost:3306/dbarticles");
        config.setUsername("root");
        config.setPassword("");
        config.setMaximumPoolSize(4);

        try (HikariDataSource dataSource = new HikariDataSource(config)) {
            // 1 - una sentencia de actualización, en una transacción
            try (Connection connection = dataSource.getConnection()) {
                connection.setAutoCommit(false);
                try (PreparedStatement statement = connection.prepareStatement(
                        "update articles set price = price * 1.1 where price < ?")) {
                    statement.setInt(1, 200);
                    int nbRows = statement.executeUpdate();
                    connection.commit();
                    IO.println(nbRows + " price(s) increased by 10 %");
                }

            long start = System.nanoTime();
            List<Future<Article>> tasks = new ArrayList<>();
            try (ExecutorService executor = Executors.newVirtualThreadPerTaskExecutor()) {
                for (int id = 1; id <= 6; id++) {
                    int articleId = id;
                    tasks.add(executor.submit(() -> getArticleSlowly(dataSource, articleId)));
                }
            } // el cierre del executor espera el fin de las seis tareas
            for (Future<Article> task : tasks) {
                IO.println(task.get());
            }
            IO.println("6 one-second queries executed in %.1f s with %d connections"
                    .formatted((System.nanoTime() - start) / 1e9, config.getMaximumPoolSize()));

            // 3 - un único valor
            try (Connection connection = dataSource.getConnection();
                 Statement statement = connection.createStatement();
                 ResultSet result = statement.executeQuery("select sum(price * currentstock) from articles")) {
                result.next();
                IO.println("Stock value: " + result.getBigDecimal(1) + " euros");
            }

            // 4 - una consulta bloqueada por otra transacción, abandonada tras un segundo
            // la transacción [blocking] modifica el artículo n.º 1 y no termina:
            // la fila permanece bloqueada
            try (Connection blocking = dataSource.getConnection()) {
                blocking.setAutoCommit(false);
                try (Statement statement = blocking.createStatement()) {
                    statement.executeUpdate("update articles set currentstock = currentstock - 1 where id = 1");
                }
                // otra conexión quiere modificar la misma fila: debe esperar el fin de [blocking]
                long chrono = System.nanoTime();
                try (Connection connection = dataSource.getConnection();
                     Statement statement = connection.createStatement()) {
                    statement.setQueryTimeout(1);
                    statement.executeUpdate("update articles set price = price * 2 where id = 1");
                } catch (SQLTimeoutException ex) {
                    IO.println(ex.getClass().getSimpleName() + " after "
                            + Math.round((System.nanoTime() - chrono) / 1e9) + " s: " + ex.getMessage());
                }
                // la transacción [blocking] no se confirmó: se revierte
                blocking.rollback();
            }
        } catch (SQLException | ExecutionException ex) {
            IO.println("Database access error (" + ex.getMessage() + ")");
        }

                result.next();

                        result.getInt(4), result.getInt(5));
            }
        }

    10.9. Ejecución por lotes

    Cada ejecución de un comando SQL implica un viaje de ida y vuelta entre la aplicación y el servidor. Cuando hay que ejecutar varios comandos SQL, pueden enviarse al SGBD en un único intercambio, en forma de lote (batch). JDBC lo admite desde la versión 2.0:

    • para un [Statement], [addBatch(sql)] agrega un comando SQL al lote;

                USER, PASSWORD);
             Statement statement = connection.createStatement()) {
            statement.execute("select name, currentstock from articles where currentstock < minimumstock + 5;"
                    + "select count(*), sum(price * currentstock) from articles");
            IO.println("Articles to watch:");
            try (ResultSet result = statement.getResultSet()) {
                while (result.next()) {
                    IO.println("  " + result.getString(1) + " : " + result.getInt(2));
                }
            }
            // pasar al siguiente resultado
            statement.getMoreResults();
            try (ResultSet result = statement.getResultSet()) {
                result.next();
                IO.println(result.getLong(1) + " articles, stock value: " + result.getBigDecimal(2)

    // inserción de n artículos mediante un lote, en una transacción, y luego eliminación de estos artículos

        try (Connection connection = DriverManager.getConnection(url, USER, PASSWORD)) {
            connection.setAutoCommit(false);
            long start = System.nanoTime();
            try (PreparedStatement statement = connection.prepareStatement(
                    "insert into articles(name, price, currentstock, minimumstock) values(?, ?, ?, ?)")) {
                for (int i = 1; i <= n; i++) {
                    statement.setString(1, "batch-" + i);
                    statement.setBigDecimal(2, BigDecimal.TEN);
                    statement.setInt(3, i);
                    statement.setInt(4, 0);
                    // los valores de los parámetros se agregan al lote
                    statement.addBatch();
                }
                int[] nbRows = statement.executeBatch();
                connection.commit();
                long duration = (System.nanoTime() - start) / 1_000_000;
                IO.println("%d insertions (%s) in %d ms: %s...".formatted(nbRows.length,
                        url.replaceFirst(".*/", ""), duration, Arrays.toString(Arrays.copyOf(nbRows, 3))));
            }
            // la tabla se devuelve a su estado anterior
            try (Statement statement = connection.createStatement()) {
                statement.executeUpdate("delete from articles where name like 'batch-%'");
                connection.commit();
            }
        }
    }

import java.sql.SQLException;
import java.sql.Statement;
import java.util.ArrayList;

// una capa [dao] que lee los tramos del impuesto desde una base de datos MySQL
public class MySqlTax implements ITaxDao {

    // códigos de error específicos de esta implementación
    public static final int ACCESS = 101, DATA = 102;

    // la consulta por defecto: los tramos deben devolverse en orden ascendente de los límites
    public static final String DEFAULT_QUERY = "select limits, coeffr, coeffn from brackets order by id";

    // tramos del impuesto
    private final List<TaxBracket> taxBrackets;

    // constructor con la consulta por defecto
    public MySqlTax(String url, String user, String password) {
        this(url, user, password, DEFAULT_QUERY);
    }

    // constructor: los tramos se leen una vez por todas
    public MySqlTax(String url, String user, String password, String query) {
        List<TaxBracket> brackets = new ArrayList<>();
        try (Connection connection = DriverManager.getConnection(url, user, password);
             Statement statement = connection.createStatement();
             ResultSet result = statement.executeQuery(query)) {
            // un tramo por fila del resultado: limit, coeffR, coeffN
            while (result.next()) {
                brackets.add(readBracket(result));
            }
        } catch (SQLException e) {
            // error de acceso a la base de datos: se envuelve en una TaxException
            throw new TaxException("Error accessing the tax brackets database", e, ACCESS);
        }
        // una tabla vacía también es un error
        if (brackets.isEmpty()) {
            throw new TaxException("The database contains no tax bracket", DATA);
        }
        // se devuelve una copia no modificable de la lista
        taxBrackets = List.copyOf(brackets);
    }

    @Override
    public List<TaxBracket> getTaxBrackets() {
        return taxBrackets;
    }

    // el tramo de la fila actual: tres columnas numéricas, sin valor NULL
    private static TaxBracket readBracket(ResultSet result) {
        try {
            BigDecimal limit = result.getBigDecimal(1);
            BigDecimal coeffR = result.getBigDecimal(2);
            BigDecimal coeffN = result.getBigDecimal(3);
            if (limit == null || coeffR == null || coeffN == null) {
                throw new TaxException("A tax bracket of the database has a NULL value", DATA);
            }
            return new TaxBracket(limit, coeffR, coeffN);
        } catch (SQLException e) {
            // una columna ausente o no numérica
            throw new TaxException("The tax brackets of the database are incorrect", e, DATA);
        }
    }
}

Las capas [business] y [ui], la clase [MySqlTax] y el programa [Main] no necesitan modificarse: solo cambian la configuración y el controlador en el classpath. Observe que la consulta de [MySqlTax] no tiene parámetros y utiliza solo SQL estándar: esto es lo que permite que cualquier SGBD la ejecute. Una capa [dao] con más funciones (búsquedas, actualizaciones) tropezaría rápidamente con las características específicas de cada SQL, como vimos antes: ahí es donde un ORM como Hibernate toma el relevo.

    10.12. Conclusión

    Este capítulo ha tratado el acceso a bases de datos mediante JDBC:

    • JDBC es un conjunto de interfaces ([Connection], [Statement], [PreparedStatement], [ResultSet], [DataSource]…), de los paquetes [java.sql] y [javax.sql] , implementadas por un controlador propio de cada SGBD (MySQL Connector/J para MySQL), que [DriverManager] selecciona a partir de la URL JDBC de la base de datos;
    • una conexión se abre lo más tarde posible y se cierra lo más pronto posible, mediante una instrucción **try-with-resources; un pool de conexiones como HikariCP, a través de la interfaz [DataSource], hace rentable esta práctica;
    • [executeQuery] ejecuta un [select] y devuelve un [ResultSet], que se recorre fila por fila con [next], leyendo las columnas, numeradas a partir de 1, con los métodos [getXxx]; [executeUpdate] ejecuta un [insert], [update], o [delete] y devuelve el número de filas modificadas;
    • los errores son [SQLException], excepciones verificadas, que devuelven un código de error propio del SGBD y un código SQLSTATE estandarizado;
    • los valores externos siempre se pasan mediante los parámetros de un [PreparedStatement] y nunca se concatenan con el texto de la consulta, lo que protege contra la inyección SQL;
    • las transacciones ([setAutoCommit(false)], [commit], [rollback], puntos de restauración) hacen atómica una secuencia de comandos SQL;
    • JDBC es bloqueante: los hilos virtuales de Java 21 permiten atender a muchos usuarios con código JDBC estándar, dentro de los límites del tamaño del pool; los lotes ([addBatch], [executeBatch]) reducen el número de intercambios con el servidor;
    • existe un modo desconectado ([CachedRowSet]), pero trabajar con objetos en memoria es hoy el dominio de los ORM.

    La versión 6 de la aplicación [Tax] demostró que, gracias a la arquitectura en capas, pasar de un archivo a una base de datos solo requiere escribir una nueva capa [dao] y modificar la configuración. El próximo capítulo creará una séptima versión de esta capa usando Hibernate, que genera por sí mismo los comandos SQL.
