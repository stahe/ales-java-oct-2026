    13.1. Introducción

    En el capítulo anterior presentamos varias aplicaciones cliente/servidor TCP/IP. Como los clientes y el servidor intercambian líneas de texto, pueden escribirse en cualquier lenguaje. El cliente solo necesita conocer el protocolo de comunicación que espera el servidor.

    Los servicios web también son aplicaciones de servidor (TCP/IP). Tienen las siguientes características:

    • están alojados en servidores web, y el protocolo de intercambio cliente/servidor es HTTP (HyperText Transfer Protocol), un protocolo construido sobre TCP/IP, que exploramos en el capítulo anterior;
    • el servicio web tiene un protocolo de comunicación estándar, independientemente del servicio prestado. Un servicio web ofrece diversos servicios: S1, S2…, Sn. Cada uno de ellos espera parámetros proporcionados por el cliente y devuelve un resultado al cliente. Para cada servicio, el cliente necesita saber:
      • cómo especificar el servicio Si;
      • la lista de parámetros que debe proporcionar y sus tipos;
      • el tipo de resultado que devuelve el servicio. Una vez conocidos estos elementos, el diálogo cliente/servidor sigue el mismo formato, sin importar qué servicio web se consulte. El código del cliente queda así estandarizado;
    • para protegerse de los ataques provenientes de Internet, muchas organizaciones abren hacia el exterior solo ciertos puertos de sus servidores: principalmente los puertos 80 (HTTP) y 443 (HTTPS) para el servicio web. Todos los demás puertos están bloqueados. En consecuencia, las aplicaciones cliente/servidor como las descritas en el capítulo anterior suelen quedar limitadas a la red privada de la organización (intranet). Alojar un servicio en un servidor web lo hace accesible a toda la comunidad de Internet;
    • el servicio web puede verse como un objeto remoto: los servicios que ofrece se convierten entonces en métodos de ese objeto. Un cliente puede usar este objeto remoto como si fuera local, a través de un objeto intermediario llamado proxy, que oculta toda la comunicación de red. Esto permite construir un cliente independiente de esta capa: si la capa cambia, no es necesario modificar el resto del cliente;
    • al igual que en las aplicaciones cliente/servidor TCP/IP del capítulo anterior, el cliente y el servidor pueden escribirse en cualquier lenguaje de programación. Intercambian líneas de texto formadas por dos partes: los encabezados requeridos por el protocolo HTTP y el cuerpo del mensaje, cuyo formato se acuerda entre el cliente y el servidor.

    13.1.1. Ayer: SOAP y WSDL

    En la década de 2000, los servicios web seguían con mayor frecuencia el estándar SOAP (Simple Object Access Protocol). El cliente enviaba una solicitud HTTP POST, cuyo cuerpo era un documento XML: un “sobre” que contenía el nombre del método invocado y sus parámetros. El servidor respondía con otro sobre XML que contenía el resultado. Cada servicio se describía mediante un documento XML en formato WSDL (Web Services Description Language), disponible en la URL del servicio seguida de [?wsdl]: enumeraba los métodos, sus parámetros y sus tipos. A partir de este documento, ciertas herramientas generaban automáticamente el proxy del servicio.

    En Java, estos servicios se escribían con la API JAX-WS: una clase anotada con [@WebService], cuyos métodos públicos (que podían anotarse con [@WebMethod]) se convertían en los métodos del servicio; la herramienta [wsimport] generaba el proxy del cliente a partir del WSDL. JAX-WS formó parte del JDK desde Java 6 hasta Java 10; se eliminó en Java 11 (JEP 320) y ahora existe fuera del JDK, con el nombre Jakarta XML Web Services. Todavía se encuentra en aplicaciones heredadas, pero los servicios nuevos rara vez lo usan. Entre las razones de este abandono están lo engorroso de los sobres XML y SOAP, la complejidad de los estándares asociados (WS-Security, WS-Addressing, etc.) y la dificultad de invocar estos servicios desde un navegador.

    13.1.2. Hoy: REST y JSON

    La mayoría de los servicios web actuales siguen el estilo REST (REpresentational State Transfer) e intercambian documentos JSON (JavaScript Object Notation, presentado en el capítulo 5). El estilo REST se basa en los siguientes principios:

    • el servicio expone recursos, cada uno designado por una URL: [/tax], [/clients/12], [/clients/12/orders];
    • se accede a estos recursos mediante los métodos (también llamados verbos) del protocolo HTTP, cada uno de los cuales tiene un significado específico;
    • el resultado de la acción se indica mediante el código de estado HTTP de la respuesta;
    • el cuerpo de las solicitudes y las respuestas es, con mayor frecuencia, un documento JSON, más compacto y simple que XML;
    • el servicio es sin estado: cada solicitud contiene toda la información necesaria para su procesamiento; el servidor no almacena ninguna información de una solicitud a la siguiente para un cliente determinado.

    Los métodos HTTP más utilizados son los siguientes:

    Uso
    Ejemplo
    GET
    Leer un recurso; los parámetros, si los hay, van en la URL

    POST

    PUT

    Código
    Significado
    200 OK

    201 Created

    Un servicio REST no tiene un equivalente obligatorio de WSDL. Sin embargo, es una práctica habitual describirlo mediante un documento OpenAPI (antes Swagger), en formato JSON o YAML, a partir del cual las herramientas pueden generar documentación, páginas de prueba y clientes. Volveremos sobre esto más adelante.

    Por último, cabe mencionar gRPC, diseñado por Google: los métodos del servicio y sus mensajes se describen en un archivo [.proto], a partir del cual las herramientas generan el servidor y el cliente, tal como se hacía en la época de WSDL; los mensajes se codifican en un formato binario compacto (Protocol Buffers) y se transmiten mediante HTTP/2. gRPC es muy eficiente y popular para la comunicación entre servicios dentro de una misma organización, pero no es adecuado para los navegadores. Está disponible en Java con la biblioteca [grpc-java], que no utilizaremos.

    13.1.3. Spring Boot y Spring MVC

    Para escribir nuestros servicios web, usaremos Spring Boot. En el capítulo 6 usamos el contenedor de inyección de dependencias de Spring Framework. Este framework también incluye un módulo web, Spring MVC, que asocia una URL y un método HTTP con un método Java mediante anotaciones: [@RestController] en la clase, [@GetMapping], [@PostMapping]… en sus métodos. Spring Boot (versión 1.0 en 2014, versión 4 en noviembre de 2025, con Spring Framework 7) simplifica la puesta en marcha de Spring:

    • se configura automáticamente la aplicación según las bibliotecas disponibles: si están presentes Spring MVC y Jackson, prepara todo lo necesario para un servicio web JSON, sin una sola línea de configuración;
    • se integra el servidor web en la aplicación: el servidor Tomcat (versión 11) es simplemente una biblioteca, lanzada por el programa principal. Por lo tanto, no es necesario instalar un servidor web o un servidor de aplicaciones aparte (Tomcat, GlassFish, WildFly…), en el cual antes se desplegaba la aplicación como un archivo [.war];
    • ofrece starters: dependencias Maven que agrupan todo lo necesario para un caso de uso específico. El starter [spring-boot-starter-webmvc] incluye Spring MVC, Tomcat, Jackson 3 (capítulo 5) y el registro de eventos (SLF4J y Logback);
    • proporciona un proyecto padre Maven, [spring-boot-starter-parent], que especifica las versiones de todas estas bibliotecas (compatibles entre sí) y un plugin de Maven, [spring-boot-maven-plugin], que lanza la aplicación ([mvn spring-boot:run]) y la empaqueta como un único archivo ejecutable, [.jar].

    Spring Boot no es la única solución: Jakarta EE (anteriormente Java EE) define el estándar de API JAX-RS (Jakarta RESTful Web Services), y frameworks como Quarkus, Micronaut y Helidon también se usan ampliamente. Spring Boot es, sin embargo, el más extendido, y se apoya de forma natural en lo que vimos en el capítulo 6.

    package wshello;

import org.springframework.web.bind.annotation.GetMapping;
import org.springframework.web.bind.annotation.PathVariable;
import org.springframework.web.bind.annotation.RestController;

// el servicio web WsHello: cada método público anotado procesa una URL
@RestController
public class HelloController {

    // la raíz del sitio: un texto de bienvenida
    @GetMapping("/")
    public String home() {
        return "WsHello web service: try /hello/{name} or /greeting/{name}";
    }

    // un "método web" convertido en URL: saluda a la señora
    // el segmento {name} de la URL se pasa al parámetro [name] del método
    // una cadena se devuelve tal cual (text/plain)
    @GetMapping("/hello/{name}")
    public String hello(@PathVariable String name) {
        return "Hello Mrs " + name;
    }

    // lo mismo con una respuesta JSON: un objeto se serializa a JSON (application/json)
    @GetMapping("/greeting/{name}")
    public Greeting greeting(@PathVariable String name) {
        return new Greeting(name, "Hello Mrs " + name);
    }

    // el resultado del método /greeting
    public record Greeting(String name, String message) {
    }
}

    Comentarios:

    • línea 8: la anotación [@RestController] designa la clase como un controlador: Spring crea una única instancia (un singleton) al iniciarse y le asigna las solicitudes HTTP cuya URL corresponde a uno de sus métodos. El resultado de cada método se envía tal cual al cliente, en el cuerpo de la respuesta;
    • líneas 12–15: la anotación [@GetMapping("/")] asocia los métodos HTTP y GET con la URL and [/] (la raíz del sitio) y con el método [home], que devuelve un texto que explica cómo usar el servicio;
    • Líneas 20–23: la URL de la plantilla (conocida como ruta) [/hello/{name}] contiene una variable [{name}]: corresponde a cualquier segmento de la URL que viene después de [/hello/]. Así, la URL [/hello/Carla%20Bruni] asigna el valor [Carla Bruni] a [{name}] (el código [%20] representa un espacio en una URL). La anotación [@PathVariable] (línea 21) indica a Spring que pase este valor al parámetro del método con el mismo nombre: esto es el enlace de datos (data binding). El método devuelve una cadena: se envía tal cual al cliente como un documento de texto (tipo [text/plain]);
    • líneas 26–29: el mismo proceso, pero el método devuelve un objeto de tipo [Greeting]. Spring lo serializa a JSON mediante Jackson (capítulo 5) y lo envía al cliente como un documento de tipo [application/json]. Este es el formato estándar de la respuesta de un servicio web REST;
    • líneas 32–33: el tipo del resultado, un record (capítulo 4), declarado dentro del controlador. Jackson sabe serializar records: cada componente se convierte en una propiedad JSON con el mismo nombre.

import java.io.IOException;
import java.net.ConnectException;
import java.net.URI;
import java.net.URLEncoder;
import java.net.http.HttpClient;
import java.net.http.HttpRequest;
import java.net.http.HttpResponse;
import java.nio.charset.StandardCharsets;
import tools.jackson.databind.json.JsonMapper;

// cliente de consola del servicio web WsHello
public class Main {

    // la respuesta JSON del servicio: mismos nombres de componentes que en el lado del servidor
    record Greeting(String name, String message) {
    }

    public static void main(String[] args) throws InterruptedException {
        // la URL del servicio se puede pasar como argumento
        URI serviceUrl = URI.create(args.length > 0 ? args[0] : "http://localhost:5100/");
        // el conversor Jackson JSON <-> objetos
        JsonMapper mapper = JsonMapper.builder().build();

        // un único cliente HTTP durante toda la duración del programa
        try (HttpClient client = HttpClient.newHttpClient()) {
            while (true) {
                // el nombre de la señora
                String input = IO.readln("Name of the lady (nothing to stop): ");
                String name = input == null ? "" : input.strip();
                if (name.isEmpty()) {
                    break;
                }
                try {
                    // el nombre se coloca en la ruta de la URL: debe codificarse en ella
                    String encodedName = URLEncoder.encode(name, StandardCharsets.UTF_8).replace("+", "%20");
                    // 1 - respuesta de texto
                    String text = get(client, serviceUrl.resolve("hello/" + encodedName));
                    IO.println("[text] " + text);
                    // 2 - respuesta JSON, deserializada en un objeto Greeting
                    String json = get(client, serviceUrl.resolve("greeting/" + encodedName));
                    Greeting greeting = mapper.readValue(json, Greeting.class);
                    IO.println("[JSON] " + greeting);
                } catch (ConnectException e) {
                    // ningún servicio escucha en esta dirección (la excepción no tiene mensaje)
                    IO.println("Error: ConnectException: connection refused (" + serviceUrl + ")");
                } catch (IOException e) {
                    // el servicio respondió con un error, o la comunicación falló
                    IO.println("Error: " + e.getClass().getSimpleName() + " : " + e.getMessage());
                }
            }
        }
    }

    // una petición GET cuyo cuerpo de respuesta se devuelve como cadena
    private static String get(HttpClient client, URI url) throws IOException, InterruptedException {
        HttpRequest request = HttpRequest.newBuilder(url).GET().build();
        HttpResponse<String> response = client.send(request, HttpResponse.BodyHandlers.ofString());
        // un código de estado distinto de 2xx es un error
        if (response.statusCode() / 100 != 2) {
            throw new IOException("the service responded " + response.statusCode() + " for " + url);
        }
        return response.body();
    }
}

    package wsoperations;

import java.util.LinkedHashMap;
import java.util.List;
import java.util.Locale;
import java.util.Map;
import java.util.function.DoubleBinaryOperator;
import org.springframework.http.HttpStatus;
import org.springframework.http.ProblemDetail;
import org.springframework.http.ResponseEntity;
import org.springframework.web.bind.annotation.GetMapping;
import org.springframework.web.bind.annotation.PathVariable;
import org.springframework.web.bind.annotation.PostMapping;
import org.springframework.web.bind.annotation.RequestBody;
import org.springframework.web.bind.annotation.RequestParam;
import org.springframework.web.bind.annotation.RestController;

// el servicio web WsOperations: las cuatro operaciones aritméticas
@RestController
public class OperationsController {

    // GET /add?a=1.5&b=2 (igual para subtract, multiply, divide)
    // [operation] proviene de la ruta de la URL, [a] y [b] de su cadena de consulta
    @GetMapping("/{operation}")
    public ResponseEntity<?> calculateGet(@PathVariable String operation,
            @RequestParam(required = false) String a, @RequestParam(required = false) String b) {
        return calculate(operation, readNumber(a), readNumber(b));
    }

    // POST /calculation con un cuerpo JSON: {"operation":"add","a":1.5,"b":2}
    // el cuerpo JSON se deserializa en el parámetro [request]
    @PostMapping("/calculation")
    public ResponseEntity<?> calculatePost(@RequestBody CalculationRequest request) {
        return calculate(request.operation(), request.a(), request.b());
    }

    // un número escrito con punto decimal, null si falta o es incorrecto
    private static Double readNumber(String text) {
        if (text == null) {
            return null;
        }
        try {
            double number = Double.parseDouble(text);
            // NaN y los infinitos se rechazan
            return Double.isFinite(number) ? number : null;
        } catch (NumberFormatException e) {
            return null;
        }
    }

    // el cálculo común a los dos métodos HTTP
    private static ResponseEntity<?> calculate(String operation, Double a, Double b) {
        // la operación solicitada, null si se desconoce
        String name = operation == null ? "" : operation.toLowerCase(Locale.ROOT);
        DoubleBinaryOperator calculation = switch (name) {
            case "add" -> (x, y) -> x + y;
            case "subtract" -> (x, y) -> x - y;
            case "multiply" -> (x, y) -> x * y;
            case "divide" -> (x, y) -> x / y;
            default -> null;
        };
        // comprobación de los parámetros: los errores se acumulan
        Map<String, List<String>> errors = new LinkedHashMap<>();
        if (calculation == null) {
            errors.put("operation", List.of("Unknown operation [" + name
                    + "]: use add, subtract, multiply or divide"));
        }
        if (a == null) {
            errors.put("a", List.of("The number a is missing or incorrect"));
        }
        if (b == null) {
            errors.put("b", List.of("The number b is missing or incorrect"));
        }
        if (!errors.isEmpty()) {
            // respuesta 400 con la lista de errores
            ProblemDetail problem = ProblemDetail.forStatus(HttpStatus.BAD_REQUEST);
            problem.setTitle("Incorrect parameters");
            problem.setProperty("errors", errors);
            return ResponseEntity.badRequest().body(problem);
        }
        // la división por cero se rechaza: respuesta 400
        if (name.equals("divide") && b == 0) {
            ProblemDetail problem = ProblemDetail.forStatusAndDetail(HttpStatus.BAD_REQUEST,
                    "The number b must be non-zero for a division");
            problem.setTitle("Division by zero");
            return ResponseEntity.badRequest().body(problem);
        }
        // respuesta 200 con el resultado en JSON
        return ResponseEntity.ok(new CalculationResult(name, a, b, calculation.applyAsDouble(a, b)));
    }

    // la solicitud de cálculo (cuerpo de la petición POST): los números ausentes del JSON son null
    public record CalculationRequest(String operation, Double a, Double b) {
    }

    // el resultado de un cálculo (cuerpo de la respuesta)
    public record CalculationResult(String operation, double a, double b, double result) {
    }
}

    • Líneas 24–28: la solicitud GET. El parámetro [operation] del método está vinculado a la variable de ruta [{operation}] ([@PathVariable]). Los parámetros [a] y [b], anotados con [@RequestParam], se enlazan con los parámetros del mismo nombre de la cadena de consulta ([?a=1.5&b=2]). Son opcionales ([required = false]): un parámetro ausente se trata como [null]; de lo contrario, Spring rechazaría con una respuesta 400 cualquier solicitud a la que le falte alguno de ellos;
    • Línea 26: [a] y [b] se declaran de tipo [String]. Podríamos haberlos declarado de tipo [double] o [Double]: Spring habría realizado entonces la conversión por sí mismo y habría rechazado un valor incorrecto con una respuesta 400 que contiene un mensaje de error genérico. Al recibirlos como cadenas, conservamos el control sobre los mensajes de error;
    • líneas 32–35: la solicitud POST. El parámetro [request], anotado con [@RequestBody], es construido por Jackson a partir del cuerpo JSON de la solicitud. Sus componentes son de tipo [Double] (línea 93), no [double]: una propiedad ausente del documento JSON se evalúa entonces como [null], lo que permite detectarla;
    • líneas 38–49: conversión de una cadena en un número; si falla, el resultado es [null]. Tanto en la URL como en JSON, los números se escriben con punto decimal: [Double.parseDouble], que es independiente del idioma del sistema, es por tanto la herramienta correcta (y no [NumberFormat], que esperaría una coma en un servidor francés, capítulo 5). También acepta los textos [NaN] e [Infinity], que rechazamos (línea 45);
    • línea 54: el nombre de la operación, en minúsculas. [Locale.ROOT] realiza la conversión sin importar el idioma del sistema;
    • líneas 55–61: la operación solicitada se representa mediante una interfaz funcional (capítulo 7), [DoubleBinaryOperator], cuyo método [applyAsDouble(double, double)] devuelve un [double]. Una expresión [switch] selecciona la lambda correspondiente a la operación; para una operación desconocida, selecciona [null];
    • líneas 63–73: los tres parámetros se validan acumulando los errores en un diccionario que asocia cada parámetro con su lista de mensajes de error. Un [LinkedHashMap] conserva el orden de inserción;
    • líneas 74–80: si se encuentra un error, se devuelve una respuesta 400. La clase [ProblemDetail] de Spring representa un documento “Problem Details”: [forStatus] lo crea con un código de estado, [setTitle] le asigna un título y [setProperty] le agrega una propiedad, en este caso [errors], la lista de errores. La clase [ResponseEntity] representa una respuesta HTTP completa: código de estado, encabezados y cuerpo. [ResponseEntity.badRequest()] prepara una respuesta 400 y [body] proporciona su cuerpo;
    • líneas 82–87: la división por cero se rechaza con una respuesta 400, cuyo documento esta vez incluye un detalle ([forStatusAndDetail]). Este rechazo es necesario: en Java, dividir un [double] por cero no lanza una excepción sino que devuelve infinito ([Double.POSITIVE_INFINITY]), que un documento JSON no puede representar (Jackson lo escribiría como una cadena, ["Infinity"]). La prueba [b == 0] compara el valor del objeto [Double] con cero: Java lo “desempaqueta” (unboxing) automáticamente;
    • línea 89: la respuesta 200, cuyo cuerpo es el objeto [CalculationResult] serializado a JSON;
    • líneas 93–98: los dos tipos intercambiados con los clientes. Estos objetos, que se utilizan únicamente para transportar datos entre dos aplicaciones, se denominan DTO (Data Transfer Object). Los records son ideales para este propósito.

    Ambos métodos del controlador devuelven el tipo [ResponseEntity<?>]: una respuesta cuyo cuerpo puede ser de cualquier tipo, en este caso un [CalculationResult] o un [ProblemDetail]. Spring examina el tipo real del cuerpo para serializarlo; asigna al documento el tipo [application/json], o [application/problem+json] para un [ProblemDetail].

    package clientwsoperations;

import java.io.IOException;
import java.net.URI;
import java.net.URLEncoder;
import java.net.http.HttpClient;
import java.net.http.HttpRequest;
import java.net.http.HttpResponse;
import java.net.http.HttpResponse.BodyHandlers;
import java.nio.charset.StandardCharsets;
import java.text.NumberFormat;
import java.text.ParsePosition;
import java.util.List;
import java.util.Map;
import tools.jackson.databind.json.JsonMapper;

// cliente de consola del servicio web WsOperations
public class Main {

    // los objetos intercambiados con el servicio (los nombres de los componentes son los del JSON)
    record CalculationRequest(String operation, double a, double b) {
    }

    record CalculationResult(String operation, double a, double b, double result) {
    }

    // una respuesta de error en el formato "Problem Details"
    record Problem(String title, String detail, Integer status, Map<String, List<String>> errors) {
    }

    // los números se escriben y se muestran en la cultura actual (fr-FR: coma decimal, en-US: punto decimal)
    private static final NumberFormat FORMAT = NumberFormat.getInstance();

    public static void main(String[] args) throws InterruptedException {
        URI serviceUrl = URI.create(args.length > 0 ? args[0] : "http://localhost:5110/");
        // el conversor JSON; Jackson 3 ignora las propiedades JSON desconocidas (instance...)
        JsonMapper mapper = JsonMapper.builder().build();

        try (HttpClient client = HttpClient.newHttpClient()) {
            while (true) {
                // ingreso de la operación y de los dos números (separador decimal de la cultura actual)
                String input = IO.readln("Operation a b (e.g.: add 1.5 2), nothing to stop: ");
                String[] fields = input == null ? new String[0] : input.strip().split("\\s+");
                if (fields.length == 0 || fields[0].isEmpty()) {
                    break;
                }
                if (fields.length != 3) {
                    IO.println("Three elements are needed: operation a b");
                    continue;
                }
                // comprobación local de los dos números, antes de cualquier llamada al servicio
                String operation = fields[0];
                Double a = readNumber(fields[1]);
                if (a == null) {
                    IO.println("Incorrect number a...");
                }
                Double b = readNumber(fields[2]);
                if (b == null) {
                    IO.println("Incorrect number b...");
                }
                if (a == null || b == null) {
                    continue;
                }
                String calculation = operation + "(" + FORMAT.format(a) + " ; " + FORMAT.format(b) + ")";

                // 1 - petición GET: en la URL, los números se escriben con punto decimal
                String url = URLEncoder.encode(operation, StandardCharsets.UTF_8) + "?a=" + a + "&b=" + b;
                try {
                    HttpRequest request = HttpRequest.newBuilder(serviceUrl.resolve(url)).GET().build();
                    HttpResponse<String> response = client.send(request, BodyHandlers.ofString());
                    if (response.statusCode() == 200) {
                        CalculationResult result = mapper.readValue(response.body(), CalculationResult.class);
                        IO.println("[GET " + url + "] " + calculation
                                + " = " + FORMAT.format(result.result()));
                    } else {
                        // fallo: se muestran el código de estado y el documento recibido, tal cual
                        IO.println("[GET " + url + "] error " + response.statusCode()
                                + " : " + response.body());
                    }
                } catch (IOException e) {
                    // el servicio es inalcanzable
                    IO.println("[GET " + url + "] error: " + e);
                }

                // 2 - petición POST: la solicitud se envía en JSON en el cuerpo de la petición
                try {
                    String json = mapper.writeValueAsString(new CalculationRequest(operation, a, b));
                    HttpRequest request = HttpRequest.newBuilder(serviceUrl.resolve("calculation"))
                            .header("Content-Type", "application/json")
                            .POST(HttpRequest.BodyPublishers.ofString(json))
                            .build();
                    HttpResponse<String> response = client.send(request, BodyHandlers.ofString());
                    if (response.statusCode() == 200) {
                        // éxito: el cuerpo contiene el resultado
                        CalculationResult result = mapper.readValue(response.body(), CalculationResult.class);
                        IO.println("[POST calculation] " + calculation + " = " + FORMAT.format(result.result()));
                    } else {
                        // fallo: el cuerpo contiene la descripción del problema
                        Problem problem = mapper.readValue(response.body(), Problem.class);
                        IO.println("[POST calculation] error " + response.statusCode() + " : " + problem.title());
                        if (problem.detail() != null) {
                            IO.println("  " + problem.detail());
                        }
                        if (problem.errors() != null) {
                            problem.errors().forEach((parameter, messages) ->
                                    IO.println("  " + parameter + " : " + String.join(" ; ", messages)));
                        }
                    }
                } catch (IOException e) {
                    // el servicio es inalcanzable
                    IO.println("[POST calculation] error: " + e);
                }
            }
        }
    }

    // un número escrito en la cultura actual, null si la entrada no es un número
    private static Double readNumber(String text) {
        ParsePosition position = new ParsePosition(0);
        Number number = FORMAT.parse(text, position);
        // la entrada debe haberse leído por completo: "2.5x" se rechaza
        return number == null || position.getIndex() != text.length() ? null : number.doubleValue();
    }
}

    }

    13.7. Información adicional

    13.7.1. Tipos de respuesta y manejo de errores

    El servicio [WsOperations] devuelve objetos [ResponseEntity<?>]: solo con las firmas de sus métodos no queda claro qué respuestas pueden producir, y el compilador no realiza ninguna verificación. El servicio [WsTax] devuelve el tipo específico de su respuesta en caso de éxito, [TaxResponse], y señala los errores mediante excepciones, que un manejador [@ExceptionHandler] convierte en respuestas. Este es el enfoque más común con Spring: el código del método solo trata el caso normal, y las herramientas (en particular el generador del documento OpenAPI) conocen el esquema JSON de la respuesta sin que se les indique explícitamente. Una prueba unitaria también puede llamar directamente a un método del controlador y examinar su resultado, sin pasar por HTTP. [ResponseEntity<T>], con un tipo específico, sigue siendo útil cuando se necesita elegir el código de estado o agregar encabezados, por ejemplo, para una respuesta 201 (Created) acompañada de su encabezado [Location]: [ResponseEntity.created(uri).body(client)].

    Un manejador [@ExceptionHandler] colocado en un controlador trata únicamente las excepciones de ese controlador. Para tratar las excepciones de todos los controladores de una aplicación, coloque los manejadores en una clase anotada con [@RestControllerAdvice]. Spring también proporciona la clase [ErrorResponseException], una excepción que transporta directamente un [ProblemDetail] y produce la respuesta correspondiente sin un manejador, y la clase [ResponseEntityExceptionHandler], que se puede extender para personalizar las respuestas a los errores detectados por el propio Spring MVC (documento JSON ilegible, tipo de documento no válido, etc.).

    13.7.2. Un prefijo común para las rutas

    Cuando varias rutas comparten un prefijo, este se especifica una sola vez con la anotación [@RequestMapping] colocada en la clase del controlador. Por ejemplo, con [@RequestMapping("/api/operations")] en la clase [OperationsController], las rutas pasan a ser [GET /api/operations/add?a=1&b=2] y [POST /api/operations/calculation], sin ningún otro cambio. Esta es también una forma sencilla de gestionar las versiones de los servicios ([/api/v1/...], [/api/v2/...]).

    13.7.3. Interceptores y validación

    Nuestros servicios validan sus propios parámetros. Spring ofrece dos mecanismos para sacar este código de los controladores:

    • interceptores: una clase que implementa la interfaz [HandlerInterceptor], registrada mediante el método [addInterceptors] de [WebMvcConfigurer], se ejecuta antes y después de los métodos del controlador; puede examinar la solicitud y responder por sí misma, sin llamar al controlador. Se usan para el registro, la medición de tiempos de respuesta, la autenticación, entre otros. Los filtros de servlet ([jakarta.servlet.Filter]) cumplen la misma función a más bajo nivel;
    • validación: con el starter [spring-boot-starter-validation] (que proporciona Hibernate Validator, la implementación de referencia de la API Jakarta Validation), los componentes de un DTO pueden anotarse con restricciones: [record TaxRequest(@NotNull Boolean married, @NotNull @Min(0) Integer children, @NotNull @Min(0) Integer salary)]. Un parámetro [@Valid @RequestBody TaxRequest request] se valida entonces antes de llamar al método, y una solicitud no válida se rechaza con una respuesta 400 “Problem Details”, como las que hemos construido.

    13.7.4. Alojamiento

    Nuestros servicios se ejecutan con [mvn spring-boot:run], lo cual es adecuado para el desarrollo. En producción:

    • primero se empaqueta la aplicación con [mvn package]: el plugin de Spring Boot genera un único archivo [.jar] “ejecutable”, que contiene la aplicación, sus dependencias y el servidor Tomcat. Basta con copiarlo al servidor y ejecutarlo con [java -jar ws-tax-9.0.jar]; la configuración se puede modificar mediante argumentos de la línea de comandos ([--server.port=80]), variables de entorno o un archivo [application.properties] colocado junto al archivo [.jar];
    • Tomcat puede exponerse directamente a Internet, pero a menudo se coloca detrás de un proxy inverso (nginx o Apache en Linux, IIS en Windows) que recibe las solicitudes HTTPS, gestiona los certificados y distribuye la carga entre varias instancias de la aplicación;
    • La aplicación también puede desplegarse como una imagen de contenedor (Docker), que el plugin de Spring Boot puede generar sin un archivo [Dockerfile]: [mvn spring-boot:build-image]. La imagen se ejecuta entonces en cualquier plataforma de contenedores, ya sea en su propio servidor o con un proveedor de alojamiento;
    • HTTPS es esencial: las propiedades [server.ssl.*] de Spring Boot configuran el certificado del servidor Tomcat cuando el servidor se expone directamente.

    13.8. Conclusión

    Este capítulo presentó los servicios web REST/JSON, sucesores de los servicios web SOAP, escritos con Spring Boot y Spring MVC. Hemos visto:

    • que un servicio web asocia URL y métodos HTTP con métodos Java mediante las anotaciones [@RestController], [@GetMapping] y [@PostMapping], y que los parámetros de estos métodos se obtienen de la ruta ([@PathVariable]), la cadena de consulta ([@RequestParam]), el cuerpo (JSON, [@RequestBody]) o el contenedor de Spring (inyección por constructor);
    • que los resultados se envían como JSON mediante Jackson, y los errores se informan mediante un código de estado y un documento “Problem Details” ([ProblemDetail], [ResponseEntity], [@ExceptionHandler]);
